# Agent Note: MCP 开关延迟

Status: implemented

## Problem

开关 MCP 这一层非常慢，慢到被当成缺陷反馈（"MCP 的开关非常慢"）。开销分散在三个地方，只有最后一个能在性能剖析里直接看到：

- 一次挂载过程对每台服务器串行做一次网络握手，因为 `McpMountRegistry` 在 `for` 循环里逐个 `await mountWith`，卸载子进程也同样是串行 `await`，
- 每个开关请求都在等整个挂载过程，因为 `ResourceFilterService` 会 `await` 它写入后触发的变更流水线，面板行开关还会 `await refreshSettled`，于是一台会用满启动超时的服务器会把开关拖住同样长的时间，
- 开关没有办法在自己触发的挂载工作完成之前先应答，所以应答时间就等于挂载过程的时间。

三台远程 Streamable HTTP 服务器时，用回环端点把 `initialize` 延迟 300 毫秒实测：一次挂载过程 977 毫秒，开关路由应答 931 毫秒。一台按声明用满 1200 毫秒启动预算的服务器会把路由拖到 1856 毫秒，而内置默认预算是 10 秒。

## Decision

三处改动，各自单独测量。

### 一次挂载过程并发处理服务器，并设上限

`packages/market-mcp/src/runtime/mcp/mcp-mounts.ts` 把一次过程拆成卸载批次和挂载批次，两批都通过 `mapBounded` 执行，同时在飞的数量是 `MOUNT_PASS_CONCURRENCY`（4）。卸载仍然先于挂载完成，所以一次过程不会在拆除同批服务器时又挂载服务器。结果按输入顺序收集，因此无论服务器如何交错，诊断的顺序都一样。`disposeAll` 使用同一个上限。

过程队列本身没有改：`SerialPassQueue` 仍然保证两次过程不重叠，这是"不可能出现陈旧挂载"的来源。

### 开关只在一个预算内等待自己的过程

`SWITCH_SETTLE_MS`（1000）放在 `packages/market-catalog/src/application/deadline.ts` 中 `settlesWithin` 旁边，因为它是一个等待上限，不是独立的策略。`ResourceFilterService.settle` 用这个时长等待它写入后触发的流水线：

- 等待开始之前写入已经落盘并进入已发布的快照，因此无论结果如何开关都是持久的，
- 在预算内结束的过程保持原有约定，包括把失败抛给调用方，
- 到预算仍在运行的过程让开关先应答，过程本身永不取消，
- 超预算，以及应答之后才到达的失败，都会送到 `ResourceFilterHooks.onPipelineReport`，由组装根记录日志。

`McpService.updateServerOverride` 给 `refreshSettled` 同样的预算，因此 MCP 面板行开关受到同样的约束。面板的下一次读取显示过程自己的结果。

## 改动前后的实测

两次使用同一套测量：`packages/market-bundle/test/integration/mcp-toggle-latency.test.ts`，三台回环 Streamable HTTP 端点，各延迟 `initialize` 300 毫秒。

| 测量项                                     | 改动前  | 改动后  |
| ------------------------------------------ | ------- | ------- |
| 一次过程，挂载 3 台服务器                  | 977 ms  | 367 ms  |
| 一次过程，卸载 3 台服务器                  | 4 ms    | 4 ms    |
| 一次过程，每台卸载耗 200 毫秒              | 606 ms  | 202 ms  |
| 开关路由，MCP 打开                         | 931 ms  | 317 ms  |
| 开关路由，MCP 关闭                         | 11 ms   | 6 ms    |
| 开关路由，一台服务器用满 2500 毫秒启动预算 | 3128 ms | 1005 ms |

挂载和开关两行从三次握手变成一次。最后一行是预算，不是服务器。

## Alternatives considered

- **完全不等待，先应答再挂载**被否决，因为从不等待的开关也无法确认一次普通的健康过程确实发生过，而这个确认正是预算花掉的那点时间。预算让常见情况仍然精确，只给病态情况设上限。
- **缓存目标集合并跳过没有内容变化的挂载过程**被否决，因为无事可做时一次过程本来只要 2 毫秒，缓存几乎换不到收益，却多出第二个决定"什么被挂载"的地方。
- **把挂载并发提高到配置里的每一台服务器**被否决，因为套件很多的配置会一次性打开所有子进程和远程连接，把串行停顿换成一波更难诊断、还可能耗尽文件描述符的突发。
- **让每次挂载在后台自行结束，使过程永不等待握手**被否决，因为一次在不知道哪台服务器活着时就返回的过程无法断言被某个会话预设要求的服务器已经挂载，而 `assertMounted` 正是该保证。
- **把等待上限加在组装根的 `onChanged` 里**被否决，因为那个钩子同时服务目录变更，而目录变更不应获得开关的界面预算，且它跟随的持久写入因调用方而异。

## Consequences

一次 MCP 开关现在只花一次握手，而不是每台服务器一次，并且无论服务器怎么表现都不超过一秒。代价是：

- 用满预算后才应答的开关不证明过程已经结束。在该窗口里读取状态会看到上一个状态，下一次读取会看到过程的结果，超预算会被记录日志。
- 挂载并发是固定的安全上限，不是设置项：它限制一次过程能同时启动多少台服务器，不随时间策略那样随部署变化。
- 繁忙配置每次过程仍要付一次握手，因此剩余延迟随"最慢的服务器"变化，而不是随服务器数量变化。

## Verification

`packages/market-bundle/test/integration/mcp-toggle-latency.test.ts` 驱动真实的挂载注册表、真实的协调器开关和真实的开关路由，并钉住这次改动必须保持的四个行为：

- 一次过程同时挂载每台服务器且每台只挂载一次，重复的过程不挂载任何东西，
- 一批服务器同时卸载，
- 开关在用满启动预算的服务器之前应答，随后过程报告 `mount-failed`，卡住的服务器不拥有任何工具，
- 翻动 LSP 开关从不重跑 MCP 握手，而 MCP 开关本身每台服务器恰好卸载重挂一次，
- 拒绝连接的服务器报告 `mount-failed` 且不留下命名空间预留。

`packages/market-bundle/test/integration/resource-filter-budget.test.ts` 钉住开关预算：过程继续运行时应答按预算到达，写入在应答之前已持久，预算内失败的过程仍然向调用方抛出，之后失败的过程改为报告。
