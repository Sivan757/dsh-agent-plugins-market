# Agent Note: MCP 开关延迟

Status: implemented

## Problem

开关 MCP 这一层非常慢，慢到被当成缺陷反馈（"MCP 的开关非常慢"）。开销分散在三个地方，只有最后一个能在性能剖析里直接看到：

- 一次挂载过程对每台服务器串行做一次网络握手，因为 `McpMountRegistry` 在 `for` 循环里逐个 `await mountWith`，卸载子进程也同样是串行 `await`，
- 每个开关请求都在等整个挂载过程，因为 `ResourceFilterService` 会 `await` 它写入后触发的变更流水线，面板行开关还会 `await refreshSettled`，于是一台会用满启动超时的服务器会把开关拖住同样长的时间，
- 开关没有办法在自己触发的挂载工作完成之前先应答，所以应答时间就等于挂载过程的时间。

三台远程 Streamable HTTP 服务器时，用回环端点把 `initialize` 延迟 300 毫秒实测：一次挂载过程 977 毫秒，开关路由应答 931 毫秒。一台按声明用满启动预算的服务器会把开关拖到那个预算，而内置默认预算是 10 秒。

## Decision

三处改动，各自单独测量。

### 一次挂载过程并发处理服务器，并设上限

`packages/market-mcp/src/runtime/mcp/mcp-mounts.ts` 把一次过程拆成卸载批次和挂载批次，两批都通过 `runBounded` 执行，同时在飞的数量是 `MOUNT_PASS_CONCURRENCY`（4）。卸载仍然先于挂载完成，所以一次过程不会在拆除同批服务器时又挂载服务器。`disposeAll` 使用同一个上限。

`runBounded` 不会整体失败：它为每个条目返回一个成功或失败的槽位，因此某条泳道抛出异常只会变成一条已报告的失败，而不会让整批被拒绝。这一点很关键，因为 `SerialPassQueue` 在一次过程被拒绝时就会释放队尾。整批被拒绝会让下一次过程在仍有泳道继续挂载时就从 `this.live` 计算要卸载的对象，而这正是本注册表要防止的陈旧挂载。失败的槽位会报告为 `mount-failed`，自行安排重试，并释放它留下的命名空间预留。

派生出的重复 serverName 在开始任何握手之前按目标顺序裁定，若胜者未能取得该名字，落选的副本会在挂载批次之后尝试接管。没有这次补挂，先到的坏副本会让服务器永久不被挂载，而之后的过程会把它描述成多余的副本。

结果按输入顺序收集，因此无论服务器如何交错，诊断的顺序都一样，而 `SerialPassQueue` 仍然保证两次过程不重叠。

### 开关只在一个预算内等待自己的过程

`ResourceFilterService.settle` 等待它写入后触发的流水线。预算是 `switchSettleMs`，由组装根通过 `resolveSwitchSettleMs` 解析，默认取 `SWITCH_SETTLE_MS`（1000）：

- 等待开始之前写入已经落盘并进入已发布的快照，因此无论结果如何开关都是持久的，
- 在预算内结束的过程保持原有约定，包括把失败抛给调用方，
- 到预算仍在运行的过程让开关先应答，过程本身永不取消，
- 超预算，以及应答之后才到达的失败，都会送到 `ResourceFilterHooks.onPipelineReport`，由组装根记录日志，
- `0` 表示从不等待，这是文档写明的方式，用即时状态换开关速度。

`McpService.updateServerOverride` 给 `refreshSettled` 同样的预算，因此 MCP 面板行开关受到同样的约束。面板的下一次读取显示过程自己的结果。

预算是配置字段而不是常量，因为它是一条用户可见的延迟策略：挂载许多慢服务器的部署可能愿意多等，而完全不想等的部署可以设为 `0`。

## Measured before and after

两次使用同一套测量：`packages/market-bundle/test/integration/mcp-toggle-latency.test.ts`，三台回环 Streamable HTTP 端点，各延迟 `initialize` 300 毫秒，同一台机器。

| 测量项                                        | 改动前  | 改动后  |
| --------------------------------------------- | ------- | ------- |
| 一次过程，挂载 1 台服务器（本测量的基本单位） | 770 ms  | 772 ms  |
| 一次过程，挂载 3 台服务器                     | 977 ms  | 346 ms  |
| 一次过程，无事可做                            | 2 ms    | 2 ms    |
| 一次过程，每台卸载耗 200 毫秒                 | 606 ms  | 211 ms  |
| 开关路由，MCP 打开                            | 931 ms  | 314 ms  |
| 开关路由，MCP 关闭                            | 11 ms   | 7 ms    |
| 开关路由，一台服务器用满 2500 毫秒启动预算    | 3128 ms | 1006 ms |

挂载和开关两行从三次握手变成一次，三台那一行与旁边的单台基准对比即可看出。最后一行是预算，不是服务器。

## Alternatives considered

- **让 `SWITCH_SETTLE_MS` 保持常量**被否决，因为它改变的是用户可见的保证，而不是描述协议或安全上限：它决定一个人要等多久。本插件已经把随部署变化的超时做成可配置的（`git.timeoutMs` 与每台服务器的 `startupTimeoutMs`），所以这里固定反而是不一致的选择。它现在是配置字段，默认值就是原来的常量值。
- **把 `MOUNT_PASS_CONCURRENCY` 也做成配置字段**被否决，因为它是遏制性上限而不是偏好。它限制一次过程能同时打开多少子进程和远程连接，调高就是文件描述符与突发连接的风险，调到一是把已经被去掉的串行停顿装回来。实现为了安全所需要的上限保持固定。
- **完全不等待，先应答再挂载**被否决为默认行为，因为从不等待的开关也无法确认一次普通的健康过程确实发生过。它作为 `0` 设置保留下来：由部署选择，而不是强加。
- **缓存目标集合并跳过没有内容变化的挂载过程**被否决，因为无事可做时一次过程本来只要 2 毫秒，缓存几乎换不到收益，却多出第二个决定"什么被挂载"的地方。
- **让每次挂载在后台自行结束，使过程永不等待握手**被否决，因为一次在不知道哪台服务器活着时就返回的过程无法断言被某个会话预设要求的服务器已经挂载，而 `assertMounted` 正是该保证。
- **把等待上限加在组装根的 `onChanged` 里**被否决，因为那个钩子同时服务目录变更，而目录变更不应获得开关的界面预算，且它跟随的持久写入因调用方而异。

## Consequences

一次 MCP 开关现在只花一次握手，而不是每台服务器一次，并且默认不超过一秒，无论服务器怎么表现。代价是：

- 用满预算后才应答的开关不证明过程已经结束。在该窗口里读取状态会看到上一个状态。下一次读取会看到过程的结果，超预算会被记录日志。
- 连着两次开关会被策略队列串行化，因此在病态配置下第二次应答可能等到两个预算。第二次写入仍然落地，因为出队的闭包是无条件写入的。健康配置下两次都在毫秒级完成。
- 挂载并发固定而开关预算可配置。这种不对称是有意的：一个约束资源，一个约束耐心。
- 繁忙配置每次过程仍要付一次握手，因此剩余延迟随"最慢的服务器"变化，而不是随服务器数量变化。
- 泳道内的失败现在是一条诊断而不是被拒绝的过程。这更好地遏制了它，也意味着挂载路径里的缺陷会表现为一台服务器失败，而不是一次过程崩坏。

## Testing

延迟测试从记录的 `initialize` 与卸载生命周期跨度断言并发，因此串行回归在任何机器速度下都会失败。它还用同一套测量里的单台过程来归一化三台过程，并把打印出的数字当作证据而不是断言。只有开关预算保留墙钟阈值，因为那是一份时间约定。

## Verification

`packages/market-bundle/test/integration/mcp-toggle-latency.test.ts` 驱动真实的挂载注册表、真实的协调器开关和真实的开关路由，并钉住这次改动必须保持的五个行为：

- 一次过程同时挂载每台服务器且每台只挂载一次，重复的过程不挂载任何东西，
- 一批服务器同时卸载，
- 开关在用满启动预算的服务器之前应答，随后过程报告 `mount-failed`，卡住的服务器不拥有任何工具，
- 翻动 LSP 开关从不重跑 MCP 握手，而 MCP 开关本身每台服务器恰好卸载重挂一次，
- 拒绝连接的服务器报告 `mount-failed` 且不留下命名空间预留。

其中三个还各自带一条回归：

- 单次挂载内部的抛出会变成一条 `mount-failed` 诊断，同批其余服务器照常挂载，下一次过程会把它们全部拆除，
- 胜者未能取得名字的重复副本会被接管挂载，最终恰好一个副本拥有该名字，
- 真正被另一个 MCP 客户端占用的命名空间仍然报告为 `foreign-mount`。

`packages/market-bundle/test/integration/resource-filter-budget.test.ts` 钉住开关预算：过程继续运行时应答按预算到达，写入在应答之前已持久，预算内失败的过程仍然向调用方抛出，之后失败的过程改为报告，`resolveSwitchSettleMs` 保留默认值并拒绝负数与非有限值，`0` 预算在过程结束前就应答且仍然存储选择。

`settle` 的流水线失败分支目前没有生产触发点。组装根里的 `runStage` 会捕获每个阶段，因此 `onChanged` 从不拒绝；该分支存在是为了这条接缝自身的约定：任何能被拒绝的钩子调用方，在预算内得到原有行为，在预算外得到一条报告。
