# Agent Note：预置来源记录 —— 市场首次运行即列出第一方集合

Status: implemented

## 问题

市场此前没有任何自带内容。全新安装打开市场页是空的，必须自己找到一个仓库地址并添加之后才有东西可看。对一个全部职责就是安装套件的插件来说，这是糟糕的首次体验：没有可浏览的内容，无法分辨安装是否正确，也没有体现这个包花了一个版本支持的 Agent Plugins v1 形态的样例。

集合本身还有归属问题。`dsh-agent-plugins`（套件创作仓库）是第一方套件的家，但用户得像添加任何第三方来源那样添加它的地址——最直接演示本插件自身格式的那批套件，反而需要最多设置步骤。

## 决定

插件只预置**一条来源记录**，指向集合仓库，别的都不带。

**是登记，不是内容。** `model/preset-source.ts` 持有这条记录——id `dsh-agent-plugins`、仓库地址、`kind: 'git'`；激活时通过 `mergeSources` 追加，也就是配置来源所用的同一条种子路径。包里没有套件，也没有 checkout。仓库仍是唯一的创作地；本包只省掉粘贴地址这一步。

**登记不发起网络访问。** 激活只写记录就结束。该来源在市场里显示为已登记但未克隆，由普通的刷新流程去拉取——与其他任何种子来源走同一条生命周期，也符合"启动不拉取 Git 更新"的既定规则。刷新按钮、显式安装、或**后台自动更新来源**都会获取它。

**没有专属开关，也没有标识。** 该记录就是 `state.json` 里的普通 `SourceRef`。模型、路由、客户端都不把它与用户自己添加的来源区分开，也没有任何设置拥有它：不想要它的用户直接删除那一行，和其他来源的删除动作完全一样。因为它是种子记录，只要种子仍在插件配置里，下次激活就会重新登记——这正是每个配置来源既有的行为。

## 被否决的替代方案

- **给它一个专属插件开关**（`builtinSource`，默认开启，负责登记与移除）。否决：专属开关把一个普通来源变成有独立生命周期的功能——跨切换保留安装记录、配置卡一行、两种语言的文案——而这一行记录本来就能用每个来源行都有的删除动作去掉。配置来源没有这种开关，这条记录就是一条配置来源。
- **把该记录标记成内置**（来源行或模型里的标识）。否决：这个标识换不到 id 之外的任何东西，却会让每个消费方多出一个分支。
- **把集合 vendored 进包内**（`suites/` 与 `lib/` 并列，登记为本地来源，用同步脚本刷新）。否决：内容在两个仓库重复，需要漂移检查才能保持可信，而且每次安装都要付出体积，只为省掉用户点一次刷新按钮就能触发的那次克隆。
- **激活时克隆该仓库。** 否决：那会让每次启动都依赖 GitHub 可达性，把本地动作变成网络动作。登记是瞬时的；拉取交给用户显式刷新。
- **删除来源时保留安装记录。** 否决：`removeSource` 本来就会连带删除该来源的安装记录，预置记录走的就是这条普通路径，不为它另造一条更温和的。

## 后果

- 全新安装会看到第一方来源，刷新一次即得到其中的套件；用户不需要输入任何仓库地址。
- 集合的内容、历史与发布都留在 `dsh-agent-plugins`；本包的发布只携带那个地址。
- 只要种子仍在插件配置里，删除那一行就是临时的——这是配置来源已经记录在案的行为。
