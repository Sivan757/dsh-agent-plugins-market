# Agent Note: 服务详情先当档案来读

Status: implemented

Revised by [失败报告先说出原因](2026-09-24-failure-report-with-cause-chain.zh.md)：状态行改为先用一句话说明识别出的失败类型，记录的诊断原文收在折叠项里。

## Problem

MCP 服务弹窗打开后先给出配置表单：一列输入框填满滚动区，工具清单在最底部，失败原因夹在两者之间。配置是这类弹窗里最低频的动作，而用户打开它要问的两件事——这个服务能不能用、它提供什么——却排在屏幕最后。

## Decision

MCP 与 LSP 两套服务弹窗共用同一个顺序：身份带（状态点、名称、状态、来源、传输方式、端点或命令）、只带原因与对应唯一恢复动作的状态行、能力区、凭据行、折叠的连接定义、高级设置折叠区、底部操作条。

- 工具清单默认渲染前八行，服务公布的工具超过八个时提供按名称过滤，需要时展开到全部。被拒绝的工具仍留在列表里，因此可以重新勾选。
- 详情与编辑分处两个弹窗：编辑入口在卡片上、启用开关的左侧，点开的是与新建流程同一个弹窗；详情弹窗只负责报告——状态、能力与凭据。状态由卡片前缘的颜色边条表达，不再用文字标签重复一遍。
- 传输方式用分段控件，每个选项注明它配置哪些字段。
- 启用开关位于底部操作条的最右侧。
- 新建服务只问名称、传输方式与该传输方式唯一必需的字段；可选的连接输入与超时留在折叠区里。模板列表与粘贴框可以把常见服务、或从其它客户端配置文件复制来的定义直接填进表单。

## Alternatives considered

- **保留一列到底的表单，只调整区块次序。** 拒绝：表单是弹窗里最慢的任务，把它放在滚动区顶部正是档案读不下去的原因。
- **给工具清单加分页。** 拒绝：分页控件藏起了服务到底提供多少工具，用一行数量加就地展开能把这个事实留住。
- **把 MCP 与 LSP 的弹窗拆成两套。** 拒绝：两者回答同样的问题，只是字段不同，共用一副骨架时用户学一次就够。

## Consequences

- 弹窗顺序成为后续服务界面的基线：新增区块要在这副梯子上找位置，而不是继续往底部追加。
- 新增样式全部使用平台 token；实际新增的只有区块副标题、折叠摘要里的生效值一行、以及工具行的网格。

## Testing

`tests/client-mcp-detail.test.ts` 锁定顺序（能力区在连接定义之上）、唯一一个启用开关、以及工具清单的截断、搜索与展开路径。`tests/client-server-config-policy.test.ts` 与 `tests/client-detail-editors.test.ts` 会先展开折叠的连接定义再编辑，这正是弹窗现在要求的操作路径。
