# Agent Note：市场给建议，安装仍由读者按下

Status: implemented

## Problem

市场跨多个来源持有约一千个套件，进入方式只有搜索与来源筛选。知道目标（「前端开发，带审查与测试」）却不知道目录的读者，没有办法要一套起步组合。

## Decision

- **市场页头的一个动作问「这个工作区用来做什么」。** 答案给出一小份带理由的选择，应用后把列表收窄到这些行；每张卡片保留自己的安装动作与确认，所以模型永远不会安装任何套件。
- **世界归服务端所有。** `purpose: 'install'` 时，`POST ai-preset` 用本次部署已扫描的目录构建候选行，浏览器只发意图。模型给出的每个 id 都要对照那份列表校验，编出来的 id 会被丢掉而不是变成一次安装。
- **已经启用的行不是候选。** 建议回答的是「该加什么」，把工作区已经在跑的摆出来只会占读者注意力。
- **建议弹窗是一个共享组件。** 它同时服务预设管理器与市场，因此搬到 `client/ui/AiSelectionModal.tsx`，用 `mode` 改变问题、文案与应用后的行为；两个功能不再互相伸手。

## Alternatives considered

- **像预设建议那样让页面自己发候选行。** 实测后否决：一千行候选会撞上宿主的请求体上限，而且浏览器会拥有一份服务端本来就有的世界。第一次实测就失败在这里，表现是裸的 `TypeError: Failed to fetch`，服务端日志里什么都没有。
- **直接安装建议的套件。** 否决：安装是逐套件的网络写入，现有的逐张确认正是读者同意它的地方。
- **只从已启用的行里推荐。** 否决：那是预设建议，管理器已经提供；市场要回答的是「该加什么」。

## Consequences

- 市场获得了「可以问」的能力，没有新增写入路径。
- 预设建议与市场建议共用同一个弹窗、同一条路由与同一个校验器，只有世界与应用步骤不同。
- 庞大的目录不再需要穿过浏览器才能到达模型。

## Verification

- 在 `market-dev` 实测：以「前端开发：审查、测试、浏览器调试，外加设计参考」按下「推荐要安装的套件」，回答 13 行（code-review、pr-review-toolkit、playwright、chrome-devtools-mcp、figma、superdesign 等）；应用后列表正好收窄为这 13 张卡片，横幅显示「AI 推荐：13 项；逐张卡片确认安装。」，清除后恢复完整列表。
- `ai-draft-routes.test.ts`（+2 条）：install 模式读目录而不是读请求；已启用的行不作为候选；目录为空时回答 400。
- 全量 2551 测试通过，门禁干净。
