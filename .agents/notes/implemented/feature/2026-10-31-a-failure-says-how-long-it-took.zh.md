# Agent Note：失败会说自己花了多久

Status: implemented

## Problem

「挂载太慢」是负责人清单里产品唯一回答不了的一条。十秒才失败的行走和四十毫秒就失败的行走读起来一样：一行原因，哪里都没有数字。而这个差别决定该查什么（握手挂住、代理不回应、还是配置错），状态数据里却没有任何字段携带它。

## Decision

- **注册表给这次尝试计时。** `mountThenReport` 是唯一知道挂载何时开始的地方，所以它在 `mountWith` 前后计时，并把 `mountMs` 放进它上报的诊断。契约在 `McpMountDiagnostic` 与 `McpStatusEntry` 上各多一个可选字段；没计时的路径不会被编造一个值。
- **行在原因旁边说这件事。** 尝试超过一秒时，卡片在原因后补上秒数（`连接超时 · 10.0s`），因为列表就是用来扫出需要处理的那一行。详情里是 `挂载用时  10013 毫秒`，可复制的诊断块里是 `mountMs: 10013`，于是一份粘贴出去的报障不必再来回一轮。
- **目前只给失败计时。** 成功的挂载要把耗时从注册表带进状态构造器，需要新增一条端口；而问题是在失败行上问的，那条路径本来就端到端存在。这条笔记记录后续，而不是假装成功的情形已经覆盖。

## Alternatives considered

- **只打日志不给界面。** 否决：提问的人正看着面板，看不见的日志行什么也没回答。
- **每一行都显示。** 暂时否决：健康行的数字是噪音，而状态数据在每次切页签时都会被读；字段是可选的，将来成功路径可以直接填，不必再改契约。
- **在客户端围着重试请求计时。** 否决：那段时间包含排队、重读状态与渲染，报出来的数字不是挂载耗时。

## Consequences

- 慢失败在打开任何东西之前就能和快失败区分开。
- 建议句与耗时并排，于是「十秒然后超时」读起来是网络问题而不是配置错误。
- 成功的挂载仍然没有耗时；那是下一片。

## Verification

- 在 `market-dev` 实测（重启宿主让新的服务端代码生效）：失败的 `kuboard` 连接器显示 `挂载用时  10013 毫秒`，复制的文本在成因链之前有 `mountMs: 10013`。10.0 秒与代理路径烧掉的连接超时一致。
- `packages/market-bundle/test/integration/mcp-status.test.ts` 钉住诊断的耗时到达行；`mcp-mounts.test.ts` 与 `mcp-backend.test.ts` 钉住失败的尝试确实记录了耗时；`packages/market-ui/test/mcp-status-render.test.ts` 钉住详情行与复制块。
