# Agent Note：用户技能面板按宿主读取器的规则发布

Status: implemented

## 问题

自建技能落到 `~/.agents/skills` 时有两种被接受的写法，而宿主的 `dsh-skill-filesystem` 读取器把同一个目录作为自己的 `user-agents` 根扫描。面板最初只列扁平 `<name>.md`，因此目录形态的 `<name>/SKILL.md` 技能在技能页里完全不可见：用户计数为零，也无法在那里启用、停用、编辑或删除。

同一处"两个读取器"还带来另外三处分歧：

- 面板用文件名或目录名注册条目，而宿主读取器注册文档声明的 `name`。同一个文件两个名字：技能在会话目录里出现两次，而 `disabled: true` 只移除面板那一份。
- 面板只要读得到文档就发布候选，包括没有 frontmatter、或 `name` 不在 kebab 语法内的文件。宿主读取器会 warn + drop 这些文件，于是面板广告了"只在装了市场插件的会话里存在"的技能。
- 没有任何测试把两个读取器绑在一起，于是以上问题全是静默发生的。

## 决策

`UserPanelStore` 接收自己要服务的文档写法，按优先级排列。技能面板同时传两种（先 `<name>/SKILL.md`，再 `<name>.md`）；命令与角色只保留扁平写法。同一名字两种写法都存在时目录形态胜出，这正是宿主读取器遇到它们的顺序。

列出、读取、编辑、删除目录形态的技能都作用于它的 `SKILL.md`。编辑保留该文档被读取时的写法。新建始终写扁平写法：面板按条目编辑单个文档，而其它工具在目录里放进 `references/`、`scripts/` 或角色文件的布局属于那个工具。删除目录形态的技能会删掉它的 `SKILL.md`，只在目录里再没有别的文件时才删除目录——插件删除自己服务的文档，绝不动它旁边的资源。

条目的名字就是其文档声明的 `name`，也就是宿主读取器从同一文件推导出的名字。面板按这个名字列出、读取、编辑、删除：查找先解析磁盘上的既有写法，再逐份比对各文档声明的名字，因此文件名与声明名不一致的文档依然可寻址。宿主读取器会拒绝的文档则以它自己的文档名列出，因为它声明的名字没有任何注册表会接受。

技能面板只发布宿主读取器会从该目录接受的文件。`skillEntryRejection` 镜像该读取器——严格 YAML frontmatter、`name` 非空且本身已是 kebab 形态（不做展示名归一化）、`description` 非空、invocation 开关合法——被拒绝的文档仍留在列表里、显示为已停用，原因写进 `validationError` 元数据，与"frontmatter 无法解析"既有情形同一形态。把它藏起来，用户就没有任何入口去找到并修好它。

`UserPanelSkillProvider` 把每个候选的 `resourceBase` 设为承载其文档的目录，因此目录形态技能里的相对 `references/…` 引用，与通过宿主读取器时的解析结果一致。

停用技能用宿主自己的控制，而不是 provider 的。面板开关把 `disable-model-invocation: true` 与 `user-invocable: false` 一起写进文档——这是该文件的所有读取器都认的唯一下线状态，因为宿主会解析这两个键、由它的消费方执行——并删掉较早的 `disabled` 键，因此更早版本停用过的条目会在第一次切换时完成迁移。面板把这对开关的取值读回为自己的停用状态；只关其中一个属于作者的编排选择（例如只允许用户调用的技能），仍算开启。命令与角色继续用它们的挂载本就会跳过的 `disabled` 键。

## 已考虑的替代方案

**只把目录形态纳入发现，写回仍走扁平路径。** 否决：通过面板的第一次编辑就会在目录旁生成第二个 `<name>.md`，同一名字留下两份文档，用户看到的文档也与宿主读取器提供的不一致。

**新建技能也采用目录形态。** 否决：这会把每个新建技能摊进一个面板毫无收益的目录，而该增删改模型编辑的正是「一条目一文档」。两种写法都作为输入被接受；面板写出的仍是扁平写法。

**递归删除技能目录。** 否决：`~/.agents` 是共享存储，`SKILL.md` 旁的文件由创建该目录的工具布置。列表行上的不可撤销删除不得越过面板所服务的文档。

**继续用文件名注册，交给下游去重。** 否决：注册表按名字去重，而"文件名候选"与"声明名候选"是两个不同的名字，下游无从判断它们描述同一个文件。

**在声明名之外继续用文档名作为条目身份。** 否决：一个条目两个名字，面板显示的名字在模型侧目录里并不存在，面板自身的控制也就作用在会话根本看不到的名字上。

**复用套件扫描器做校验。** 否决：那个解析器是刻意宽松的——Codex 展示名会被归一化成 kebab，prose 字段有逐行兜底——因为套件技能只有本插件一个加载者。而 `~/.agents/skills` 里的面板文档同时被宿主读取器读取，后者规则更严，所以一致性只能取自后者。

**把被拒绝的文档从列表中移除。** 否决：条目会从唯一能修好它的界面消失。

**把文档改名出发现形态（`<name>.md.disabled`，某些技能编辑器这么做）。** 否决：这能一次性对所有工具卸载，但同时改写了用户的目录布局、打扰软链与外部工具，还需要一份恢复记录——而 invocation 开关对在宿主执行它的所有位置都能达到同样效果，且不动任何文件。

**只改写渲染出来的目录文本。** 否决：把条目从模型当轮目录里藏起来，`skill` 工具与 `/name` 仍会加载它，面板报告的就不是真正的停用状态。

**继续用 provider 侧不发候选。** 否决：这正是本 Note 要修的失败——面板省略的技能仍会被宿主读取器从同一目录提供，那个开关其实什么也没控制。

## 后果

技能页会列出会话能从 `~/.agents/skills` 加载的全部技能，其用户计数与磁盘一致。面板的启停开关、编辑器与删除动作现在也作用于其它工具创作的技能，而不再是由宿主读取器无管理地提供。

声明的名字与文件名不同时不再产生重复技能：面板显示的就是声明名，也就是会话看到的那个名字，而 `path` 仍然指出它所在的文件。

被拒绝的文档现在显示为已停用并带出原因，而不再是一个幻影技能；它的启停开关无法单独打开——拒绝结论是从文档重新计算的，修法是改文档。

面板刻意比套件扫描更严：套件里的 `name: Presentations` 会被归一化并加载，而 `~/.agents/skills` 里的同一份 frontmatter 会被拒绝，因为宿主读取器会把它丢掉。

开关现在能让技能在任何 profile 下都不再加载，无论提供它的是面板还是宿主读取器。它不移除文件：其它工具仍然会发现该技能，手工编辑这对 invocation 开关与点开关是同一个控制。

## 验证

`tests/user-panels.test.ts` 覆盖目录形态技能的列出、编辑、删除，搬空后目录的删除，两种写法并存时的优先级，扁平新建，仅扁平的面板，按写法区分的 `resourceBase`，以文档声明的名字命名条目并由编辑/删除把该名字解析回文件，把 invocation 开关对读作停用状态且只关其中一个仍算开启，以及每一条被拒绝文档的路径（YAML 无法解析、展示名、缺 description、缺 frontmatter）都留在列表里显示为已停用并给出原因。`tests/user-panel-surface.test.ts` 覆盖开关写出这对开关并删掉 `disabled`，以及拒绝校验失败的文档。`tests/panel-resources.test.ts` 覆盖通过 HTTP 层使用的名字 id 访问同一条目。
