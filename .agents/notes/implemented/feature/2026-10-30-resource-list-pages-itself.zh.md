# Agent Note：资源集合自己分页

Status: implemented

## Problem

市场页打开时要把读者的整个清单都渲染出来。一个真实 profile 里就有 1,000 个套件，其中 971 个未安装，而共享渲染器一次挂载了每一张卡：打开该分区实测首屏卡片耗时 306ms，文档里留下 16,000 个节点。这个代价每次打开都要付，随读者新增来源而增长，也让之后每一次筛选都要重渲染一千张卡。

## Decision

- **在渲染器里，一次只渲染一页卡片。** `ResourceSurface` 渲染 `RESOURCE_PAGE_SIZE`（120）条，集合末尾的哨兵进入视野时再追加下一页。列表是共享的，所以每个界面都自动得到同一条规则。
- **按钮承担同一个动作。** 哨兵就是一个「再多显示 N 个」按钮：没有 `IntersectionObserver` 也能用，是可看见的入口而不是隐形触发器，键盘与读屏读者按的正是它。
- **筛选与搜索在分页之前、对全集运行。** 标签计数仍是筛选命中的数量，命中第一页之外的搜索仍然找得到；分页只影响渲染。
- **筛选或搜索后回到第一页。** 保留页码会把读者丢进一个他从未滚动过的集合中段。

## Alternatives considered

- **虚拟化网格。** 暂时否决：卡片高度可变、两种视图模式、共享渲染器，测量与焦点处理都要大改；分页用五分之一代码去掉实测成本。
- **调大每页数量直到看起来合适。** 否决：任何固定数字都在这台机器合适、在那台不合适；120 让促成这次改动的那个 profile 打开仍在一帧内，也仍能填满大视口。
- **只在市场页分页。** 否决：成本属于共享列表，按界面各做一份分页，正是渲染器要消灭的第二种实现。

## Consequences

- 想看到第 900 个套件的读者要滚动或按「再多显示」，而不是它已经挂载好了；标签计数仍然告诉他集合有多大。
- DOM 规模与读者看过多少成正比，而不是与他的清单大小成正比。
- 每页数量只是常数一处：改它会同时改变所有界面。

## Verification

- `packages/market-ui/test/resource-surface-paging.test.ts` 钉住每页数量、追加、搜索能命中第一页之外的条目，以及搜索后回到第一页。
- `market-dev` profile 对构建产物、同一 profile、同一份 1,000 套件清单实测：首屏卡片从 306ms 降到 55ms，文档节点从 16,046 降到 2,498；滚到底部后列表从 120 增长到 240，按钮文案为「再多显示 120 个」。
