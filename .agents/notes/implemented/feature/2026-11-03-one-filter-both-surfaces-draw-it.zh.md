# Agent Note：只有一个筛选，两个界面从同一张表取

Status: implemented

## Problem

每个列表都按自己的轴切分。市场藏起未安装的套件，服务面板藏起「需处理」，用户内容面板除了来源还藏起已停用的行，语言引擎又重复了一遍「需处理」，预设管理器则藏起所有未开启的卡片。于是同一条工具栏在每个页签问的是不同的问题，而其中两个问题（是否安装、是否开启）本来就已经由卡片的边条与状态词回答了。

## Decision

- **唯一的筛选是「谁提供了这一行」**：套件带来的，还是人写的。每个面用自己的词汇称呼这两半（项目文件对用户级文件、套件服务对直连），因为产品的名词本来就因面而异；但机制、位置、顺序、零计数隐藏全部共享。
- **这张表只存在于一个模块里，两个界面都从它取。** `ui/surface-facets.ts` 声明每个工作区页签的用词并构造分支；设置页各面板与预设管理器都调用 `surfaceProviderCuts`，各自只提供「这一行来自谁」。任何一边都无法新增另一边没有的筛选。
- **只有单一来源的面不画筛选。** 市场与钩子列表只可能有套件行：「全部 1000」旁边挂一个「套件 1000」是把同一张清单列两遍。这条规则写在表里，不是每个调用点的条件判断。
- **状态筛选全部移除。** 失败的连接器、停用的技能、未安装的套件——卡片的边条、状态词与动作已经说了。筛选唯一多做的是把其它行藏起来。

## Alternatives considered

- **在每个面保留统一的「已启用/已停用」筛选。** 否决：负责人的意思是这个状态列表里已经看得到，而统一的、没用的筛选并不比多样的、有用的筛选更诚实。
- **各面板保留自己的分支、只对齐文案。** 否决：文案本来就已对齐；分歧在于问的是哪个问题。
- **把这张表放进 `workspace/`。** 被架构门禁否决：`ui/` 不能从 `workspace/` 导入，而画这条筛选的渲染面在 `ui/`。模块已移入 `ui/`。

## Consequences

- 九个面与九个预设面在同一份数据上显示同一行筛选。
- 新的列表只要声明它的两种来源就得到这条筛选，无法发明第三种轴。
- 预设管理器与设置页可以逐字段对比：筛选完全一致，剩下的差异是数据范围与可提供的动作。

## Verification

- 在 `market-dev` 两个界面实测。设置页：技能 全部 157 · 套件 157；快捷指令 全部 22 · 套件 21 · 用户 1；连接器 全部 5 · 套件 2 · 用户 3；系统提示词 全部 1 · 用户级 1；输出风格 全部 1 · 套件 1；市场与钩子无筛选。预设管理器报告同样的行，其中系统提示词读作 全部 3 · 项目 2 · 用户级 1，因为它读的是会话的完整链——同一筛选，数据更宽。
- `surface-facets.test.ts` 钉住这张表：双来源面按同一顺序给两个分支，单来源面不给分支，未知行两边都不算。
- 全量测试通过（2526），架构门禁干净，三条断言旧筛选的测试已改为共享筛选。
