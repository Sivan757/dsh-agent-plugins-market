# Agent Note：MCP 掉线要传到会话里

Status: implemented

## Problem

MCP 服务器连上之后再死掉，几乎不留痕迹。监督器在重试期间保留工具注册，所以模型下一次请求仍能看到这些工具，而每次调用都在传输层失败；重试预算耗尽后工具被注销，下一次请求就只是少了一批工具。唯一的持久记录是一行进程日志。对话里没有任何东西说明「有一项能力消失了」。

宿主客户端自己的机制止步于重连：有界退避、重置预算的稳定窗口，以及注册表的 `tools/change`——它告诉你工具集变了，却不说为什么变、是谁变的。`ToolDefinition` 不带来源字段，因此 `mcp__signoz__query_metrics` 这样的名字是 harness 手里唯一的归属线索。本插件知道得更多：挂载注册表把派生的 `serverName` 映射回套件与声明，bridge 也早就在发布每一次连接相位（`McpConnectionObservation`）。这些信息一路走到状态面板就停了——而那个面板要先打开才看得到。

## Decision

- **一次折叠，两个出口。** `McpHealthMonitor` 把监督器的相位边沿收敛为一次故障最多三种转换：第二次失败尝试时的 `degraded`、预算耗尽时的 `stopped`、以及重新提供工具并稳定五秒之后的 `recovered`。判断由边沿驱动；恢复是唯一被延后的检查——每次故障一个定时器，任何后续边沿都会取消它。监督器会让崩溃循环的服务器在每次尝试上都真的连上，若按每次连接都报一次恢复，一次故障就会被讲成一串自相矛盾的消息。
- **发布侧新增的是订阅，不是新的发布者。** 连接注册表上的 `observeMcpConnections` 就是那道缝：监视器通过它订阅，因此没有任何监督器知道监视器存在，状态面板读到的仍是同一份快照。这建立在[掉线的 MCP 连接会说明发生了什么](../bug-fix/2026-10-30-mcp-connection-observations.zh.md)之上，那份记录确立了相位与面板；它的记载仍然成立，只是注册表多了这个订阅。
- **通知到达会话。** `mountMcpHealthNotices` 为每次转换注入一条 user 角色消息，来源是 `notice` 形态（`plugin-market-mcp`）：折叠后是一行本地化摘要，正文写明服务、所属套件、第几次尝试、下次重试与最近错误。投递只用 `agent.inject`，绝不用 `followup`——连接变化永远不开启新回合，空闲会话会在下一次本要用到这些工具的请求里收到它。每个会话各有一条消息身份：跨收件箱共用一个消息会越过会话边界。
- **健康段落到达模型。** `mountMcpHealthSection` 在 `MCP_SERVERS + 1` 注册一个全局 `systemPrompt.section`，所有服务器健康时渲染为空串。它是进程级的，因为挂载本身就是进程级的：MCP 工具对整个进程注册一次，而不是按工作区注册，所以每个 agent 读到同一份清单。这里设 `interpolate: false`，因为套件 id 是作者写下的文本，必须原样到达模型。
- **段落固定英文，通知双语。** 段落与 harness 自带的 MCP 段落、工具描述一起被读取，这正是 `host-locale.ts` 已经为子代理目录记录过的分工。通知是界面文案，走那张宿主本地化表，缺省为中文。

## Alternatives considered

- **轮询状态接口并比对相邻两次读取。** 否决：它凭空造出第二个时钟，每个 tick 都付出目录读取的代价，仍会漏掉两次轮询之间的转换。监督器本来就在边沿发布。
- **面向模型的 `mcp_health` 工具。** 否决：它要求模型先怀疑出了问题，而这里的失败模式恰恰是模型悄悄绕开缺失的工具——那正是没人会想起来去问的情形。
- **用 `followup` 唤醒会话。** 否决：重连不是用户请求，短暂故障会自行开启一个没人要求的回合，而那次回答没有任何提问为它买单。
- **每一次重试边沿都通知。** 否决：第一次重试就恢复的抖动不是新闻，按退避台阶逐条通知会把一次故障变成十条消息。
- **只把事实放进系统提示词。** 否决仅此一条渠道：段落说明「现在缺什么」，但对话的读者什么也看不到；说出「这事发生了」的是通知。
- **把重新挂载当作恢复来报告。** 否决：bridge 释放后重新连接就是普通的重新挂载路径，把每条这样的路径都算作恢复，会为从未失败过的连接发出恢复通知。监视器只为它已经通知过的故障保留标记，因此下一次连接仍能把这件事故收尾。
- **在第一个 `connected` 边沿就宣布恢复。** 在独立宿主里做了真实抖动测试之后否决：崩溃循环的服务器每 1.2 秒连上再死掉，会话因此每个循环都收到一条恢复通知紧跟一条新的故障通知，模型还据此报告了一次已经失效的「恢复」。恢复现在要等满一个在线窗口，这与监督器自己重置预算时问的稳定性问题是同一个。
- **给每个 bridge 工具的执行错误包上连接状态。** 暂缓而非否决：那是下一层，而且它改变的是每个工具的执行路径，而不是一道发布缝。

## Consequences

- 掉线的服务对失去它的会话可见，用读者的语言呈现，不必打开面板；模型可以点名缺失的能力，而不是静默绕开。
- 健康的会话不付任何代价：段落为空，也不产生通知。
- `mcpEnhanced: false`（宿主兼容后端）不产生通知，因为那个客户端不通过这道缝发布连接相位。服务指南写明了这条边界。
- 已通知过的故障在 bridge 被释放时保留一个标记，因此重新挂载后的连接仍算作恢复。标记按服务器名各一条，由下一次连接或下一次故障清除。

## Testing

- `packages/market-mcp/test/mcp-health.test.ts` 钉住通知阈值、一次故障只通知一次、停止通知、跨 bridge 重建的恢复，以及监听器抛错的隔离。
- `packages/market-runtime/test/mcp-health-section.test.ts` 与 `mcp-health-notice.test.ts` 钉住两种语言的渲染文本、健康时的空段落，以及投递契约：每个会话一条消息、不唤醒、一个会话拒收不影响其它会话。
- `packages/market-bundle/test/integration/mcp-health-wiring.test.ts` 从 `recordMcpConnection` 穿过折叠跑到通知与段落，因此任何一处漏订阅的接线改动都会在这里失败。
