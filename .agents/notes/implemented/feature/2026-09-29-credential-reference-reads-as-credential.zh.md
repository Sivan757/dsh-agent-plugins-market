# Agent Note: A credential reference reads as a credential

Status: implemented

## Problem

同一个请求头机密有两个操作面，而两者互相矛盾。详情弹窗给出的是**凭据配置区**：每个引用一条只写不读的 `SettingsSecretField`，带已配置徽标、保存与删除控件，以及一行说明哪个座位在用它。服务编辑器给出的却是文档原文——`Authorization` 旁边一个普通输入框里躺着 `${CONTEXT7_API_KEY:-}`——于是"编辑这个服务"的弹窗根本没有地方设置它需要的机密，而引用语法被当成了值来读。

两者之所以不同，是因为它们本就是两样东西：文档里确实存着引用，机密则存在宿主凭据库里。让它们看起来像同一件事的两种做法的，是呈现方式。

## Decision

**凭据配置区改为共享 UI，编辑器也挂它。** `McpCredentialFields` 移到 `src/client/ui/`，并把配置区需要的两个助手一起带上——`credentialUsage`（哪个座位在用哪个引用）与 `credentialRefOf`（一个值**是不是**恰好一个引用）。详情弹窗与服务编辑器渲染同一个区块，机密在两处用同一种方式写入。编辑器把凭据线作为 prop 接进来，并在表单视图里、针对会用到引用的 MCP 文档渲染该区块：LSP 挂载路径没有凭据解析器，因此不挂此区块，JSON 视图则展示整份文档。

**恰好是一个引用的值，读作它指名的凭据。** 请求头或环境变量里的 `${NAME}` 与 `${NAME:-}` 变成一枚 chip——盾牌图标加名字，原文做 tooltip——激活该 chip 会把这一行交回文本输入框，文档里没有任何东西变得够不到。值里含别的内容时（URL 查询串、非空默认值、字面 token）仍然按文本显示，chip 未覆盖的其它座位同样如此。

## Alternatives considered

**凭据区留在详情弹窗，编辑器里的引用继续按文本显示。** 这是最省的改法，也正是这次报障的状态。否决：编辑器才是编辑这个服务的地方；为了设置这个服务需要的机密而把用户支到另一个弹窗去，这个问题本身就是不一致。

**把引用在输入框里美化一下。** `<input>` 只能渲染一个字符串：它承载不了图标、状态或第二个目标，所谓"好看"顶多是换个字色。

**把挂载会解析的每个座位都做成 chip。** 引用也可能出现在 `args`、`cwd` 或 URL 里。那些是单值字段，值通常是混合文本；在那里做 chip，要么盖住周围文字，要么在一个并非纯引用的值上误触发。两张映射表——请求头与环境变量——才是引用真正待的地方，也是这次做 chip 的两处。

**干脆把引用语法从表单里藏掉。** 看起来更干净，但文档才是权威：夺走回到原文的路，等于让表单对它正在编辑的东西说谎。

**顺手提供"把字面值存成凭据"。** 把 `Bearer eyJ…` 变成 `${NAME}` 意味着起名字、写机密、改写文档，还要保持该座位的语义；那是一件独立的功能，而这次报障说的是一个已经存在的引用该怎么读。

## Consequences

- 文档里用到引用的 MCP 服务，无论是详情还是编辑器打开，都会显示凭据配置区与被 chip 化的值；机密只经由宿主控件写入一次。
- 编辑器里的 chip 是按钮：键盘用户激活它即可到达原文。
- 表单未做 chip 的座位——URL 查询串、`cwd`、参数——里的引用仍按文本显示，字面机密仍是字面机密。
- LSP 编辑器永远不显示该区块：它的挂载解析的是插件路径，不是凭据。

## Testing

- `tests/client-detail-editors.test.ts` —— 请求头引用渲染成携带引用名、以原文作 title 的 chip，激活前不存在值输入框；文档用到的引用在表单视图出现凭据配置区，在 JSON 视图让位。
- 详情弹窗的配置区与写一次路径未变：`tests/client-credentials.test.ts` 继续覆盖线适配器，编辑器测试覆盖表单自身行为。
