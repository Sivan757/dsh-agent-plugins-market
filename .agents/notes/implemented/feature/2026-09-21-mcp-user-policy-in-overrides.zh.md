# Agent Note: MCP 用户策略走覆盖记录

Status: implemented

## Problem

用户无法调整套件服务一次工具调用可以花多久。桥接的默认值（每次调用 60 000 毫秒、启动 10 000 毫秒）与套件的 `com.deepseek.harness` 声明是仅有的两个来源，因此自建服务里一次合法运行超过一分钟的工具调用会以 `MCP error -32001: Request timed out` 失败，市场里没有任何入口能提高这个上限。

工具选择同样够不着。命名空间可以声明 `enabledTools` / `disabledTools`，内置桥接也同时执行两者，但用户想关掉某一个工具，只能去改一个下次刷新就会被覆盖的包文件。

## Decision

逐服务器覆盖记录继续作为用户策略唯一的存放位置，并增加三个套件无法替用户拥有的字段：

- `toolCallTimeoutMs` 与 `startupTimeoutMs` —— 超时是一次普通覆盖。用户存下的值优先，用户没设时由套件声明补上，两者都没有时以内置默认值兜底。
- `disabledTools` —— 用户关闭的工具名。

**工具过滤只能收紧。** 生效拒绝列表是套件自身条目与用户条目的并集，生效白名单就是套件声明的白名单，保持不变。用户无法放开套件排除在外的工具，套件的收窄因此在每一次用户编辑之后依然成立。

**未声明的启动超时保持缺省。** 两层都没有设置时，桥接配置不写 `startupTimeoutMs`：内置桥接在连接时套用自己的默认值，无法执行启动超时的宿主兼容模式也能继续挂载该服务。

**保存把策略与文档一起提交。** `POST server-config/save` 接收 `policy: { toolCallTimeoutMs, startupTimeoutMs }`，数值表示设置，`null` 表示清除并回到继承。字段缺省表示保留已存的值，客户端只发送相对已加载基线发生变化的字段，用户在当前后端没有动过的值因此不会跟着跑到拒绝它的另一个后端。服务端校验正整数且落在 2 147 483 647 的定时器范围内，其余取值以可读原因拒绝，客户端因此可以就地显示原因，该值不会悄无声息地消失。保存成功后编辑器重新读取服务，策略视图、占位内容与脏值基线都按已存下的内容呈现。

**保存配置替换连接字段，保留策略字段。** 提交的文档已经涵盖 `url`/`headers`/`env`/`args`，因此这几个覆盖字段从记录中清除，而 `enabled`、`auth`、`disabledTools`、两个超时与连接文档全部保留。残留的连接字段会盖过刚刚保存的配置，因为 `applyOverride` 把它叠在已存的 `config` 之上。

**可移植文档保持可移植。** `schemas/1.0.0|1.1.0/mcp.schema.json` 给每个服务定义都加了 `additionalProperties: false`，因此超时走覆盖记录，绝不进入 `mcp.json` 正文或编辑器的 JSON 文本；编辑器文档是去掉策略字段之后的连接形状。

**宿主兼容的限制有明确说明。** `@deepseek-ai/dsh-mcp-client` 会拒绝带有启动超时或工具过滤的挂载配置。会让两者取值的保存与工具勾选在入口处被拒绝，并给出可读原因；服务编辑器禁用启动超时输入并说明原因，工具勾选框在同一条说明下以禁用状态渲染。工具调用超时在两个后端都可用，因为宿主客户端会执行它。在内置客户端生效期间存下的启动超时，在禁用输入旁保留一个清除操作，因此无需切回内置后端就能移除它。

### 勾选状态模型

面板的工具列表是四者的并集：服务已注册的工具、套件白名单、套件拒绝列表、用户拒绝列表。被拒绝的工具会从实时注册表中消失，因此让它在列表里继续出现、并且还能重新打开的依据，就是存下的这几个列表。

一行呈现三种状态之一：

- **允许** —— 落在套件白名单内（或套件没有声明白名单），且不在任何拒绝列表中。已勾选，可编辑。
- **用户拒绝** —— 出现在 `disabledTools` 中。未勾选，可编辑。
- **套件限定** —— 不在已声明的白名单内，或出现在套件的拒绝列表中。未勾选，固定不可改，并标注为套件声明。

`setMcpServerTool(suiteKey, serverKey, tool, enabled)` 把拒绝写入覆盖记录；最后一条拒绝被清除时该字段随之删除，因此没有任何拒绝的服务完全不携带工具策略。改动通过启用开关所用的同一条 `notifyChanged(true)` + `refreshSettled()` 路径立即重新挂载。

## Alternatives considered

- **把上限放进服务配置文档。** 否决：可移植 schema 收紧了服务定义，文档会校验失败，而且客户端专属字段本来也无法随包刷新一起携带。
- **把用户的拒绝并入 `enabledTools`。** 否决：这会抹掉「套件声明」与「用户选择」的区别，这样写出的用户列表会在下一次读取时放开套件白名单。
- **让客户端提交整份生效策略并替换已存记录。** 否决：编辑器拿不到字面凭据值，逐字写入会丢掉被遮蔽的键。逐字段写入并用 `null` 表示清除，可以保持记录其余部分完整。
- **沿用连接字段那种「命名空间策略优先」的次序。** 否决于工具列表与超时：套件声明是用户可以改动的默认值，这个次序会让已声明的服务完全无法修改该字段。
- **越界的超时直接丢弃该字段。** 否决于保存入口：静默丢弃读起来就是保存成功，用户无从得知该值没有生效。存储仍然丢弃格式错误的字段，因为手工编辑的文件不能拖垮记录其余部分。
- **只下发一份生效拒绝列表，在客户端反推套件那一份。** 否决：同时被两层拒绝的工具会被读成「用户拒绝」，并给出一个不会生效的开关。线上数据把套件白名单、套件拒绝列表、用户拒绝列表分开携带。
- **在宿主后端隐藏工具勾选框。** 否决：一个说明原因后就地禁用的控件让限制可被发现，切回内置客户端即可恢复，不必重新理解页面。

## Consequences

- 自建或较慢的服务得到它需要的时间，既不必离开内置桥接，也不必改套件。
- 拒绝既可持久也可撤销：注册表丢弃该工具之后它仍留在列表中，重新勾选即删除已存的名字。
- 宿主兼容后端只挂载它能执行的策略，无法执行时明确说出该动哪个控件。
- 覆盖记录增加三个字段，因此 `sanitizeOverrides`、`sanitizeOverridePatch`、`mergeOverridePatch` 一起扩展；记录继续作为用户策略唯一的持久化位置。
- `disabledTools` 与 `args` 一样整体替换，空列表以「无此字段」持久化。

## Testing

`tests/mcp-overrides.test.ts` 覆盖新字段的清洗、超时越界的丢弃、`parseTimeoutPatch` 的拒绝、合并语义与 `withoutPolicyFields`。`tests/mcp-config.test.ts` 钉住优先级：用户超时覆盖套件、拒绝列表取并集、套件白名单不被放宽、未声明的启动超时不出现在挂载配置里。`tests/server-config.test.ts` 通过真实文件系统驱动保存：报告已存超时及其来源、清除连接残留、保留 `enabled`/`auth`/`disabledTools`、`null` 清除、越界拒绝、工具勾选写入与字段删除，以及宿主后端拒绝启动超时与工具勾选。`tests/routes.test.ts` 检查线上解析，`tests/mcp-status.test.ts` 检查上报的列表。`tests/client-server-config-policy.test.ts` 渲染折叠区、占位值、非法状态与保存后的重新读取，并驱动保存请求体：只发送发生变化的超时、清空字段发出 `null`、host 后端下只改工具调用超时时不带上已存的启动超时、以及清除操作在该后端移除启动超时。`tests/client-mcp-detail.test.ts` 渲染三种勾选状态、宿主后端的禁用与只读的外部挂载行。
