# Agent Note: 横跨六个面的通用翻译层

Status: implemented

## Problem

市场渲染的上游 catalog 以英文撰写，因此 `zh` 部署看到的是中文界面里嵌着英文数据。套件描述，技能、快捷指令、专家三者的描述，以及 MCP 每个工具的说明，全都原样进入面板。[描述本地化 note](2026-10-03-description-localization.md) 只补上了一个面上的一个字段；同一个缺陷在其余各面渲染的每一条描述上依然存在。

catalog 不归我们编辑。一个 source 是别人仓库的 checkout，每次更新都会刷新，所以翻译不能写回 manifest。它必须放在 catalog 旁边，在输出的路上应用。

三条约束决定了答案的形态。它必须零配置可用——全新安装、没有代理、没有 API key、没有配置模型路由，也要能收敛到中文。它绝不能让面板比它所替换的英文更差，因此每一条失败路径都终止于上游原文。它还必须避开模型读到的那一份：进入模型上下文的 system prompt 与工具描述，和人在屏幕上看到的是两种不同的产物。

## Decision

本地化是市场渲染时经过的一层，而不是某张卡片代码路径里的一步。一条 translation unit 描述一个可翻字段；一条有序 provider 链为它作答；一份按内容寻址的缓存记住答案；每个面渲染译文，同时把上游原文保持为它一直以来的那个标识。

### 一条单元，六个面

单元携带面（`market`、`skills`、`commands`、`agents`、`mcp`、`lsp`）、实体在该面内的稳定 id、角色（`description`，整篇分块翻译的正文用 `document`——见[文档翻译那份记录](2026-10-05-document-translation-chunked-and-lazy.md)）与上游原文。六个面汇入同一个收集器；一个实体已经付过费的文本会直接答复携带同一文本的其他实体：缓存键仍指向实体，文件因此依旧记录「为谁翻过什么」，而提供方的工作按文本索引，重复出现的字符串每次会话只花一次调用，无论被多少字段承载——且每次会话读到的字段都会写回自己的键，之后的启动直接从磁盘供出。在本机 catalog（911 个 suite）上实测：该层会发送的 suite、技能、快捷指令与专家描述共 5,055 条、1.35M 字符，其中 4,892 条文本、1.33M 字符互不重复；把那 911 个 suite 携带的 4,161 份文档全部读一遍，又得到 36,503 条分块文本，其中 34,729 条互不重复——即分别有 3.2% 与 4.9% 的待发送文本是重复的。每批最多 20 条文本、最多 6,400 源字符、同时最多 3 批，因此一次慢调用不会扩散成数百个请求——而且没有任何一次调用索取的输出超过模型跳被允许产出的量：预算是按这次调用实际携带的源文本量算出来的，不是按它装了几条文本。超过一块的文本会像文档正文那样拆分，而不是整条发出，因此再长的上游字段也越不过那份预算。

| 面       | 译文                     |
| -------- | ------------------------ |
| 市场     | 套件描述                 |
| 技能     | 技能描述                 |
| 快捷指令 | 命令描述                 |
| 专家     | 角色描述                 |
| MCP      | 每个工具一行             |
| LSP      | 无 —— 该条目没有描述字段 |

### 有序回退链

provider 按固定顺序运行：Google Translate、Microsoft Translator、用户自己的默认模型、上游原文。第一个作答的胜出；抛错、超时或返回条数不符的 provider 被跳过。两个公开端点都不需要 key、不需要配置，这正是该能力开箱即用的来源；模型留在链上，作为配置了它的部署可用的最高质量档。

Google 先试、给 3 秒；Microsoft 给 15 秒；模型给 30 秒。失败的 provider 在本次进程内被摘出链外，因此一个不可达的端点只付一次超时，而不是每批一次，因为被阻断的网络会把连接挂住而不是拒绝它。但「摘出」不是永久：把翻译开关重新打开、或清空缓存，都会让链回到干净状态，因为这两者都是用户在要求重新翻译。没有这一步，一次被截断的生成会让模型这一跳直到进程重启都不再参与——开关仍显示「开」，每次读取都报告没有待办，屏幕上也没有任何东西解释这件事。本机实测：Google 走代理 0.26 秒作答，无代理时挂过 4 秒；Microsoft 无需任何认证、直连 0.38 秒作答。

### 缓存与键

译文以目标 locale、单元的面、id、角色与原文，以及 provider 链的标识，共同做 SHA-256 摘要作为缓存键。按内容寻址意味着重写了文本的实体会重新翻译，而只是提升版本号的实体保留译文。条目不过期；设置卡里有一个清空整个缓存的按钮，下次打开面板会重新翻译。

provider 标识放进键里是刻意的。换了引擎的部署必须让旧引擎产出的文本失效，而不是把它当作新引擎的产出继续供出；另一种做法——给每条记录一个「可升级」标记——是第二套状态机，而它买不到键已经给不了的东西。记录里的 `provider` 字段仍然保留，那是给翻看文件的运维人员看的，不参与判定。

### 哪些文本需要翻译

文本要不要发出去，看的是「它是不是已经写在目标语言里」，判据是主导文字而不是「是否出现过」某个字。过去只要出现一个汉字就被判定为「已经是中文或已是双语」而拒发，这对真正要紧的那批文本是错的：在本机市场的真实来源里量下来，成千上万个 800 字符的文档块是英文散文，只是里面点了中文术语、引了中文报错、或与中文表头同处一张表格，这些块全被拒发——283 篇真实文档因此只翻了一半，而面板却报告说已经安定。现在的规则是：拉丁字母数不少于汉字数的文本照发，只有汉字占主导的才拒发。已经中文的文本送到 provider 会原样返回（用 Microsoft 端点实测），因此剩下的拒发不产生费用、也是诚实的：被拒的那部分本来就写在读者要的语言里。

### 遮蔽

两个公开引擎都会破坏技术文本：它们改写裸尖括号、转义 HTML、吞掉字面换行。一批文本发出之前，行内代码、URL、尖括号片段、`${VAR}` 引用和一份固定术语表（`MCP`、`LSP`、`DSH`、`CLI`、`API`、`JSON`、`HTTP`、`URL`、`SDK`）会被替换成引擎原样透传的占位符。答案返回后还原占位符，且每一个都必须恰好出现一次；没通过这项校验的一批直接丢弃，不入缓存。

### 渲染：只有描述会变

名称从不翻译。它是用户输入、搜索、排序、复制、并与上游文档对照的那个标识，收集器不会为它产出任何单元，因此两种视图渲染的是同一个字符串。描述没有这重身份，所以直接渲染译文，作者原文只隔着面板视图开关的一次按下。

### 设置与作用域

只有英文界面被跳过：面板显示的本就是作者原文，为它排队调用等于花额度复现输入。其余每一种偏好都会翻译，因为其余每一种偏好渲染的都是市场的中文字典——`bindHostLocale` 对 `ja` 与 `zh-Hant` 给出的就是 `zh` 读者看到的那份文案——而目标语言跟着这份字典走，不跟着偏好的标签走。因此 `ja` 读者拿到的是中文界面旁的中文译文，而不是中文标签旁的日文；`zh-Hant` 读者拿到的是简体而不是繁体。目标语言只有一个函数（`resolveTranslationTarget`），开关默认值与每个面的闸门读的都是同一个谓词，三者因此无法漂移；将来若要加第二本字典，应该在那里加一个分支，而不是在别处再读一遍偏好。一个设置开关可以关掉这一层：链清空后，所有面渲染上游原文。这一层从不触碰模型读到的那一份：注入会话的 system prompt 与工具描述保持作者撰写时的语言。

## Alternatives considered

**在客户端翻译。** 因分层被否。`src/client/**` 不得 import `node:**`，也不持有持久缓存；浏览器侧翻译器会在每次页面加载时重新调用 provider，且无法跨重启记住结果。浏览器这一半渲染 node 这一半算好的译文，不自己算。

**只做两个免费机器翻译端点。** 被否：术语保真度是通用机器翻译引擎的弱项——`skill`、`suite`、`surface` 回来的译法前后不一致，专有名词在两次调用之间漂移。用户自己的模型留在链上，作为可以被告知如何呈现本领域词汇的那一档；只有部署配置了它，链才会走到它。

**把 provider 从缓存键里去掉。** 被否：键就只剩内容，换了引擎的部署会永远继续供出旧引擎的文本。手工失效或靠版本号失效是伪装的版本标记；把 provider 标识折进键里让未命中自动发生。

**按来源分片缓存。** 本轮不做。设计文档提议一个来源一个文件，因为单文件每次 flush 都要整份原子重写；在本 catalog 的体量下整份文档只有几兆，清空按钮已能让用户随时把增长归零。分片会引入多文件迁移与并发写问题，而这份代价目前还没有被测量到。

## Consequences

面板绝不比这一层出现之前更差：断网、没有模型路由、端点限流或缓存文件损坏时，每个面渲染的都与它此前渲染的上游原文完全一致；第二次启动进程用零次 provider 调用供出同样的文本。每个面都在译文旁保留作者原文，因此它的搜索、排序、复制、斜杠调用与 `aria-label` 读到的名称与作者写的一致。

代价是：

- **公开端点无 key，因此没有承诺。** 限流或端点下线会静默降级到下一级，既不通知用户，也没有「当前生效 provider」的读数可供诊断。
- **机器翻译质量低于模型。** 遮蔽层保护代码、路径与固定术语表，模型档仍是配置了它的部署的质量上限。
- **被阻断的网络下首次调用要付一次超时。** 熔断把它限制为一次；Google 让位后 Microsoft 在半秒内作答。
- **缓存随 catalog 增长。** 按内容寻址的键只增不减；清空按钮是用户把增长归零的那一环，而单文件每次 flush 都要整份重写。

## Testing

这里的每一项机制都在树的副本里对着「故意撤回的修复」重跑过，且都让对应用例变红。恢复「每条文本固定输出预算」（`512 × 文本条数`）会让钉住按源定预算的两个翻译器用例、以及那次原本会被截断的调用变红。撤掉熔断恢复的任一半——清空缓存或开关重新打开——会让钉住它的 localizer 与 settings-namespace 用例变红。恢复「出现汉字即拒发」会让两条 `needsTranslation` 用例、以及「英文段落引用中文却报告无待办」的文档路径用例变红。把偏好标签直接当作目标语言，会让 `zh-CN`、`zh-Hant`、`ja`、`en`、`en-US` 的门禁一致性用例、以及 localizer 的目标用例变红。
