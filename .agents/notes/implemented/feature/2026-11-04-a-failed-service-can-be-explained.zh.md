# Agent Note：失败的服务可以被解释，也只能被解释

Status: implemented

## Problem

失败了的连接器或语言引擎会显示状态词、代码、原因，有时还有一串归因。这些是构建者能确立的事实；读者接下来通常需要的是「下一步做什么」，而面板能陈述问题，却从不给出下一步。

## Decision

- **一个只读的 AI 动作，放在详情弹窗里。** `POST ai-diagnose` 接收这一行已经展示的事实，回答一段散文：最可能的原因、一到三步操作，以及事实不足以判断时缺的是哪一条。答案渲染在状态条下方，也就是读者本来就在看的位置。
- **它什么都改不了。** 不重试、不重启、不编辑：路由只是一次模型调用加一个字符串，该行保持原来的状态，所以错误的解释只花一次阅读。
- **事实在服务端有界并重建。** 状态、代码、原因、归因、传输方式与挂载耗时，各自裁剪到契约上限。端点与命令故意留在浏览器：端点可能在查询串里带凭据，解释的分量不如泄漏重。
- **按钮说清它问的是什么。** 失败行给「让 AI 解释这次失败」；其它状态（含停用）给「让 AI 解释这个状态」，因为让一个停用的服务解释它的失败是标签层面的谎话。
- **两个族共用同一个组件。** MCP 与 LSP 共用 `DiagnoseBlock` 和同一份提示词（只有族名不同），因为读者的问题与复核步骤是一样的。

## Alternatives considered

- **给 MCP 与 LSP 各写一份解释。** 否决：同一个读者问题要养两套提示词、两种答案形状、两处漂移。
- **把端点一并送去，好让模型判断可达性。** 否决：端点是最可能携带凭据的字段，而面板自己的原因已经说明了失败在哪一步。
- **每一行都提供。** 否决：已挂载的连接器没什么可解释，一个常常回答「一切正常」的按钮只会教会读者忽略它。
- **让模型给出修复建议并直接执行。** 否决：那是凭一次推断去改配置。插件自己的重试与重启才是修复，而且它们是确定性的。

## Consequences

- 两个服务面各获得一条「下一步」的解释，彼此没有新增依赖。
- 每次解释是一次有界的模型调用；答案会说明用了哪个模型，提供方报了用量时沿用起草面相同的字段形状。
- 失败与其它状态是两个键，将来新增状态可以直接归到正确的一边，不必猜翻译。

## Verification

- 在 `market-dev` 实测：停用的 TypeScript 服务详情里显示「让 AI 解释这个状态」，答案把 `state: disabled` 当作唯一事实，建议启用并观察该行，并明说缺哪条信息，而不是编一条。
- `diagnose-block.test.ts`（4 条）：请求带上事实；答案就地渲染；提供方限流用共享的那句话；状态措辞与失败措辞不同；没有答案之前不渲染任何正文。
- `ai-draft-routes.test.ts`（+3 条）：诊断会报出产生它的路由；未知族或缺少状态时在调用模型前拒绝；单次请求携带的量有界。
- 全量 2549 测试通过，门禁干净。
