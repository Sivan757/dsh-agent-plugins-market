# Agent Note: 详情页整篇翻译文档正文，分块进行，收在折叠区里

Status: implemented

## Problem

用户希望详情页的 Markdown 预览在开启翻译时同时给出两种语言——上一行原文、下方译文——并且懒加载，交互参考 read-frog。此前那次调研把代价量了出来，结论并不是这个诉求所假设的样子。

预览经由宿主的 `MarkdownText` 渲染（`@deepseek-ai/dsh-client-ui-primitives@0.2.0-rc.2`，从 `src/client/ui/MarkdownDocument.tsx` 进入），它接收整篇文档、返回一棵树。它的块级粒度确实存在，但只在包内：已发布 tarball 只带 `lib/`，因此 `package.json` 声明的 `./src/*` 子路径解析不到文件，`markdown/parse.ts` 与 `markdown/render.tsx` 都拿不到。自己切分源码、每块各挂一个 `MarkdownText` 的渲染结果是字节等价的——实测 6 篇真实文档，18 个边界用例中 16 个一致——但它要求客户端包里再装一套 markdown 解析器（实测 +85,565 B minified、+24,527 B gzip，用仓库自带的 esbuild 量得），永久耦合宿主不对外导出的私有语法扩展（`cjkFriendlyStrong`、`mathCompatibility`），而且会踩碎宿主自己的间距契约：`MarkdownText.module.css` 把首尾子元素的 margin 清零，一块一个容器就得在本地把整篇文档的纵向节奏重建一遍。即便加了缓解，仍有两个用例是错的：链接引用定义与脚注各自住在自己的顶层块里，切分之后会被原样渲染成字面量。

把数字摆上桌之后，用户选了更便宜的那个形状：整篇译文放在折叠区里，不做逐块插入。这个形状有它自己的一条硬约束，而且是用户自己点出来的：一篇文档远长于任何单次 provider 请求能承载的量。

## Decision

文档整篇翻译，分块传输。

`chunkDocument`（`src/application/translation/document.ts`）按空行切分正文，在不切断段落的范围内把段落打包到预算上限，只对超过预算的段落做拆分，并把每段围栏代码整体保留为原样块。每个块都带着它在原文里后面那段文本——行尾、空行、下一个块之前的空白——`Catalog.translateDocument` 原样再发出去，而不是自己合成一个分隔符：什么都没翻的正文因此逐字节还原。用 `'\n\n'` 连接看起来等价，其实不是：列表项里缩进的围栏就是一个块的边界，它前面只有作者写下的一个换行，合成出来的空行会让列表项变松散、并把代码块移出 `<li>`。

### 块大小是推导出来的，不是拍出来的

链上最紧的一跳是模型而不是那两个公开端点：`runtime/host/llm-translator.ts` 按这次调用实际携带的源文本量来定输出预算（`outputTokenBudget`，按每个源字符约 0.6 token 估算，下限 512、上限 4,096）；一次触顶的生成会让整批失败，并且把模型这一跳从链上摘掉。

膨胀比是量出来的而不是假设的：本仓库自带的 90 组英中对照里，中文一侧的字符数是英文的 0.461（中位数）到 0.617（最坏；把一组 36 字符的占位对照算进来是 0.621）。折成 _token_ 的那一步是估算而不是实测，文中也如此标注——这棵树里没有任何分词器——按每个汉字约 0.7 token 估算，最坏情况约合每个源字符 0.43 token。预算常量取每个源字符 0.6 token，比这份估算留出约 40% 余量，同时让一次携带满额 `MAX_BATCH_CHARS`（6,400 源字符）的调用仍落在 4,096 上限之内。

真正的紧约束是模型跳自己的输出预算，而不是厂商的请求上限：这条链调用的两个公开端点是两家自家翻译挂件所用的消费级端点，而不是那些常被引用的 Cloud API，后者的「每请求上限」并不适用于它们，因此这里不声明任何请求体量数字。若把某一跳改到有正式文档的 API 上，`MAX_BATCH_CHARS` 就得按那个 API 自己的上限重新推导。

### 一批的量由字符数与条数共同约束

单靠 `MAX_BATCH_SIZE` 约束的是一次调用带几条文本，而不是带多少文本，于是二十个文档块会向模型跳索取数倍于它被允许产出的输出。`MAX_BATCH_CHARS`（6,400）就是翻译器据以定输出预算的那个数的输入一半：`TranslationLocalizer.pump` 在下一条文本会顶穿上限时停止装批，`schedulePump` 在已达上限时立刻开批。超过整份预算的单条文本永远不会被丢弃——它自己开一批、独自运行；这之所以成立，只因为进入队列的文本都不可能那么长。

描述类流量同样受约束，并没有被豁免：`Catalog.translateFields` 用同一个分块器处理描述，超过一块的字段因此分块传输、并用它自己那份原文分隔符拼回。真实目录里量到的最长描述是 1,428 字符，9,969 条里有 59 条超过一块，所以这很少见——但在旧的「每条文本固定输出预算」（约 1,113 源字符）下，这 59 条每一条都是「生成被截断、provider 被摘掉」的入口。

### 角色槽保住了既有缓存

文档块与同一实体的描述共享 surface 与 id，因此必须在缓存键里区分开。`TranslationUnit.role`（`description` | `document`）就是这个槽，默认值是 `description`——磁盘上每一条既有记录被写入时，这一层只有这一个角色。于是 `translationKey` 对不指明角色的单元算出的摘要完全相同：没有既有记录会移位，升级也不会重新付费。

### 服务端自己重读条目，页面只报名字

`PanelResourceStore.translateDocument(id)` 自己读取条目，并在分块前剥掉 frontmatter：frontmatter 是概览块已经展示过的元数据，而让 provider 翻 YAML 只会拿回不再能解析的 YAML。路由（`POST <user-panel>/<kind>/entry/translation`）只携带 `{ name }`，别的一概不带，页面上的脚本因此无法拿它选定的文本去花掉使用者的翻译额度。

### 译文在读者要它的时候才去读

`src/client/ui/DocumentTranslation.tsx` 在文档下方渲染一行折叠区。首次读取发生在展开时、绝不在挂载时，随后由共用的 `pollUntilTranslated` 反复重读直到 `pending` 归零——文本因此是逐渐填满的：已进缓存的块立刻出现，仍在途的块显示其原文段落，并在行注里说明这一点。这一区只出现在它能说出点什么的地方：翻译关闭时，或界面语言本身就是文档的撰写语言时，它什么都不渲染、也什么都不读。

## Alternatives considered

**在每个块下方插入译文，即 read-frog 的形状、也是用户最初的诉求。** 用户在量出代价后否决了它：客户端包里多一套 markdown 解析器、永久耦合已发布包不导出的语法扩展、宿主间距契约要在本地重建，外加两个跨块用例始终是错的。read-frog 真正贡献的交互——把译文叠在其原文之下、按屏上可见范围门控工作量——在这个形状里保留了下来。

**照 read-frog 的做法把译文节点注入已渲染的 DOM。** 否决：read-frog 是运行在别人页面上的浏览器扩展，注入 DOM 是它唯一的选择。这里渲染树归 React 所有，而 `MarkdownText` 是 memo 组件、其子节点来自 `useMemo` 的元素数组；从外面插进去的节点不在 React 的子节点序列里，该容器下一次渲染就会与它们冲突。

**不解析 markdown，只按空行切。** 否决：与整篇渲染对比实测，一个带围栏保护的按空行切分器会静默改变真实内容——它把松散列表变成三个紧凑列表，并把列表项里的第二段提到 `<li>` 之外。读者拿来对照的是撰写出来的那份文档，译文视图因此不得重排它。

**整篇作为一个单元送出去，让 provider 去拒绝。** 否决：用户点名的就是这个风险，而模型跳的输出上限会截断而不是拒绝——那会把一份残缺的译文当成完整的呈现出来。

**每条文本给固定输出预算，只约束批次。** 否决：一次调用要产出的是它手上那份源文本的膨胀量，因此一个「每条固定」的常量不可能同时适配二十条短描述和一条长描述。实测 512 token 只够约 1,113 个源字符，而真实目录里就有更长的描述；超出时是被截断而不是被拒绝，于是整批失败、provider 被摘掉。

**把译文正文渲染成纯文本而不是 markdown。** 否决：机器翻译会破坏 markdown 结构（`#` 与列表标记会掉、URL 会移位），纯文本会把每篇文档变成一整面墙的散文。交给 `MarkdownText` 渲染降级的是排版而不是安全性：原始 HTML 被丢弃、链接协议被限制，与原文文档完全同一套规则，因此 provider 返回什么都渲染得安全。

**连围栏代码一起翻。** 否决：被要求翻译示例的 provider 会连示例里的代码一起翻，而一篇示例再也跑不起来的 `SKILL.md` 比不翻更糟。代码块永远不发送，也永远不产生费用。

**用块的下标而不是块的文本做键。** 否决：键是文本的摘要，因此被编辑过的段落会落空重翻，而它未受影响的邻居仍从缓存取用；用下标则任何一次编辑都会让整篇文档重新付费。

## Consequences

读者按需打开译文正文，只为真正看过的块付费，中途关闭时已经落地的块都会保留。代价是每块一条缓存记录——55 KB 的 changelog 是几十个小摘要而不是一条大记录——以及第一行中文要等第一批返回之后才出现。

markdown 的机器翻译是尽力而为。标题与列表通常能保住；provider 掉了某个标记时，降级的是那一段的排版，仅此而已。

译文正文是文档去掉 frontmatter 之后的正文。上方的概览块已经展示了那些字段，所以没有信息丢失，但折叠区并不是上方文件的逐字节镜像。

批次预算是这一层范围内的改动：描述异常长的部署现在会形成比以前更小的批次。那只是请求条数的变化，从不是正确性的损失，而且用的就是模型跳一直以来的那个上限。

译文正文现在是「原文正文、散文块被逐一替换」：每个块前后的分隔符、行尾与空行都是作者自己写下的。还有块在排队时，文档渲染出来与文件本身完全一致——这正是折叠区能与上方预览逐处对照的前提。

## Testing

`tests/document-chunks.test.ts` 钉住分块器：预算成立、放得下的段落保持完整、超长段落按自身换行拆分、围栏保住其中的空行且永不进入 provider、未闭合围栏到文末都算代码、输出预算盖得住实测最坏膨胀、一整批仍落在单次调用上限之内，并且本仓库自带的每一篇 Markdown 文档都能被 `chunks.map(chunk => chunk.text + chunk.separator).join('')` 逐字节还原——语料是三百多篇真实文档，因此只在 fixture 上成立的分隔符规则会被挂出来。促使这次修复的那个形状另有单独用例：列表文本与缩进围栏之间作者写下的那一个换行，回来时仍然是一个换行。

`tests/translation-document.test.ts` 让真实的 `Catalog` 跑在 fixture suite 上：一次读取以原文作答并报告它排入队列的量、落定后按顺序拼回译文、第二次读取由缓存服务、围栏块不出现在任何 provider 批次里且原样出现在输出中、英文界面什么都不翻、没有 provider 链的部署什么都不排队、完全没有文本的正文原样返回、作者写的结尾换行得以保留、列表项里的围栏保住作者写下的那一个换行、store 读取会剥掉它拿到的 frontmatter。

`tests/translation-cache.test.ts` 钉住角色槽：不指明角色的单元保持它原本就有的键，而同一实体的文档块不会替它的描述作答。`tests/translation-localizer.test.ts` 钉住批次预算：一次调用不越上限，而超过整份预算的单条文本仍能独自运行。

`tests/client-document-translation.test.ts` 挂载这一区：翻译关闭或英文界面下什么都不渲染、什么都不读；文档只在展开那一行之后才被读取；在最后一块落地之前行注一直显示生成中；读取失败时报告失败而不是给出一篇文档。

`tests/routes.test.ts` 逐名断言每个面板的六条路由路径——用的是客户端构造 URL 的同一个 helper——并实际驱动翻译路由：响应形状、只有条目名会随请求出行、以及不带名字的请求体在询问 store 之前就被拒绝。

以上每一条都在「故意撤回修复」之后重跑并失败过：关掉围栏识别让 5 个用例变红，改动任一尺寸常量让钉住它的用例变红，把角色槽改回固定值让缓存用例变红，去掉展开闸门让 4 个用例变红。

分隔符规则同样如此，验证是在树的副本里做的：恢复旧分块器与它的空行连接会让 12 个用例变红，其中包含两个往返用例和列表项围栏那个用例；把翻译器的预算常量压到盖不住实测最坏膨胀，会让 `tests/document-chunks.test.ts` 里那条推导断言变红。围绕它新增的用例也都经过撤回验证：恢复「每条文本固定输出预算」让钉住按源定预算的两个翻译器用例变红，撤掉描述分块让描述往返用例变红，恢复「出现汉字即拒发」让两条 `needsTranslation` 用例与「英文段落在文档路径上被静默跳过」那个用例变红，把偏好标签直接当作目标语言会让 `zh-CN`、`zh-Hant`、`ja`、`en`、`en-US` 的门禁一致性用例变红。
