# Agent Note：起草要对着真模型验、要标价、要能撤回

Status: implemented

## Problem

起草的几个面在上线时只有路由与字段组件的测试，从来没有真模型回答过。第一次实测就抓到了测试抓不到的缺陷：两条 AI 路由的成功响应缺少本仓库统一的 `ok: true` 信封，而客户端的共享请求助手不接受没有它的响应，于是**每一次成功的起草都变成读者眼里的 `draft failed: 200`**。单测之所以是绿的，是因为它们只看路由自己的响应体，从未经过客户端的解析。

同一轮实测还暴露两个产品缺口：一次起草花掉了部署的 token 却从不说明；起草替换了编辑器里的正文，却没有回退的路。

## Decision

- **实测是 AI 面上线的一部分。** 每个面都对着部署的模型起草过一次（技能、快捷指令、专家、输出风格、系统提示词），预设管理器也建议过一次选择，创建后随即移除。信封缺陷就是在这里发现的，修在路由上，并在两条路由测试里钉住。
- **成功响应带 `ok: true`。** 两条 AI 路由改用本仓库的写入信封，测试断言它存在，因为对客户端来说「缺了它」和「调用失败」无法区分。
- **每个答案都报出代价。** `AiDraftResult` 与 `AiPresetSuggestion` 带上提供方给的 `usage`，字段把模型与输入/输出 token 打在同一行。提供方没给用时用短句，不编一个 0。
- **草稿可撤回。** 字段记住草稿到达时编辑器里的内容，撤销按钮把它放回去：只编辑一段正文的面恢复整篇文档；输出风格编辑器把草稿拆成两个字段，所以恢复它自己的快照。
- **辅助调用只要路由接受的最省思考档。** 阶梯是 `off`、`minimal`、`low`，最后才是部署自己的选择。起草与翻译都是机械活，而这个 profile 选的是 `max`，每次调用白花好几秒。

## Alternatives considered

- **只信单测直接上线。** 否决：测试验的是服务端契约，缺陷正在服务端响应体与客户端解析之间。
- **让客户端接受没有 `ok` 的响应。** 否决：本插件其余所有写入都带 `ok: true`，在一处容忍它的缺失只会掩盖下一次遗漏。
- **用文本长度估算 token。** 否决：提供方的账目精确且顺手可得，估算只会多出第二个互相矛盾的数字。
- **始终转发部署的思考档。** 实测后否决：`max` 下一次起草约 11 秒，最省可接受档 7–10 秒，而翻译对页面上的每条文本都在做同样的调用。

## Consequences

- 一次起草现在会说明模型与代价，并且一次按下就能撤回。
- 翻译继承了更省的思考档，对一个调用频繁得多的面是同样的改善。
- `ok: true` 的缺失是上线前抓到的真实缺陷，路由测试已经钉住它。
