# Agent Note: zip 条目写入走有界槽位

Status: implemented

## Problem

`extractZip` 把每个完成条目的 `writeZipEntry` promise 推进一个无界数组，最后统一 await。unzip 流是同步驱动 `onfile` 的，所以整个归档会在第一个写入完成前就把它自己的写入全部排上：两万条目的 zip 会一次性向进程索要两万个文件描述符。Linux 与 macOS 扛得住；Windows 在第 8192 个左右拒绝，并表现为 11812 条未处理的 `EMFILE` rejection，让整次测试运行失败——尽管被测的那个守卫本身已经完成了它的工作。

同一段代码还会在写入尚未落定时就上报守卫失败。`extractZip` 抛出时仍有条目写入在跑，而调用方会在自己的 `finally` 里删除暂存目录——一个尚未启动的写入会把它自己的路径重新创建出来，于是清理以 `ENOTEMPTY` 失败。

## Decision

写入走一组固定的 32 个槽位。每个完成的条目追加到某个槽位的链条上，因此提取持续流动的同时最多只有 32 个描述符打开。流处理期间记录下的失败会把尚未启动的写入变成空操作，而 `extractZip` 只在所有链条都落定之后才上报。

"先落定再上报"正是暂存目录可以被安全删除的前提：`archiveInstall` 删除 `.extract` 时，不允许还有任何东西在往里写。错误统一汇入既有的 `failure` 槽位而不是让某条链 rejection，因此报告出来的仍是最早的失败，也不会留下无人观察的 rejection。

## Consequences

触发条目数守卫的归档不会再先把条目落盘再被拒：条目上限那个用例在 Windows 上从 20.5s 降到 1.0s，本地从 31.9s 降到 3.1s——守卫现在是让工作停下来，而不是和它赛跑。

正常归档的吞吐在实践中不受影响——这些写入本身很小，而 32 个在途远超磁盘在常规提取中同时挂起的量。

## Alternatives considered

**在排队处逐个 await。** 每个归档只占一个描述符，彻底消除尖峰，代价是每次安装每个条目都要一次完整往返。

**只约束成功路径，失败时保留原有的扇出。** 尖峰来自扇出本身，而触发守卫的归档恰恰是那些剩余条目我们并不想写的归档。

**提取前抬高进程描述符上限。** 上限是宿主的，不是我们的；一个插件去改它会影响同一会话里的所有其他消费者，而且对下一个更大的归档来说扇出依旧是错的。

## Testing

`tests/zip-bomb.test.ts` 构造一个 20010 条目的 zip 并断言条目上限拒绝；这正是本次改动前在 Windows 上失败的那个用例。它的同类用例覆盖解包后的 tar 遍历。`tests/source-acquisition.test.ts` 端到端覆盖完整归档安装，包括暂存目录切换与单层包装目录归一，因此成功路径上的"先落定再上报"同样被覆盖。
