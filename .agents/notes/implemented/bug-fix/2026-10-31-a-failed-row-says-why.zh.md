# Agent Note：失败的行在自己的行上说明原因

Status: implemented

## Problem

开发 profile 上有三个连接器挂载失败，而它们的三行说的是同一句话：**连接失败**。原因（超时、TLS 握手失败）与建议（「确认服务可达…」）其实都存在，但只在详情对话框里，隔一次点击。一个以「哪些行需要处理」为目的的列表却无法说明**为什么**，读者要么把三个对话框都打开，要么把它们当成同一种失败。

语言引擎同理：从未挂载成功的服务器在打开前只显示「挂载失败」。

## Decision

- **卡片陈述原因，详情保留建议。** `failureCause` 接收分类后的引导句，返回第一个分隔符之前的那一小句（「连接超时」「TLS 握手失败」「Connection timed out」），于是这一行回答了列表读者唯一的问题。连接器与语言引擎的行把它渲染在卡片的警告标签里。
- **整句仍留在可行动的地方。** 详情对话框保留带操作指引的完整句子与重试按钮，没有把任何东西挪出可达范围。
- **没有原因的行保持沉默。** 已挂载但最近一次调用失败的行仍用自己的措辞；分类器认不出的行什么都不显示，而不是猜一个。

## Alternatives considered

- **把整句引导语放上卡片。** 否决：它是 24–60 个字符，在列表视图里无论如何都会被截到最前几个字；能活过窄列的正是「原因」那一段。
- **为每种失败形状另加短键。** 否决：两种语言要多 23 个键，重复已有句子的前半句，句子一改还要改两处。
- **只靠标签，把原因留给 tooltip。** 否决：扫描时 tooltip 不可见，而这一行的目的恰恰是可扫描。

## Consequences

- 三个失败的连接器一眼读作三个不同的问题。
- 引导句没有分隔符的语言保留整句，由行自己截断。
- 分类器仍是唯一决定「这是什么失败」的地方；卡片只展示它的短形式。

## Verification

- 在 `market-dev` 对真实失败连接器实测：kuboard 读作 连接超时、GitLab 读作 TLS 握手失败、signoz 读作 连接超时——改前三者都是 连接失败。
- `packages/market-ui/test/client-failure-guidance.test.ts` 断言两种语言下的切分、无分隔符时的原样返回，以及以分隔符开头的句子保持完整。
- `packages/market-ui/test/mcp-status-render.test.ts` 断言被拒绝的连接在卡片警告标签里渲染「拒绝」形状，而不是超时建议。
- 四个类型检查、`check:refactor` 与全量测试通过。
