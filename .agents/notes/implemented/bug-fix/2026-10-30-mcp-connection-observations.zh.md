# Agent Note：MCP 连接断开会说明发生了什么

Status: implemented

## Problem

一个连上之后又死掉的服务，在监管器重试期间仍保留着工具注册，于是状态行继续显示「已连接」且没有任何原因，面板无法把它和健康服务区分开。这次中断唯一的记录只有一行日志：连接丢失、16 秒后重试、第 5/10 次。退避会增长到每次 30 秒，一次中断允许十次，用户可以盯着一条看起来健康的行好几分钟，每次调用都失败，却没有任何信息说明原因或何时结束。

挂载诊断覆盖不到这种情况。它描述的是从未连上的服务；一条已经建立的连接掉线不会产生诊断，而重试路径只写日志。

## Decision

- **监管器公布自己的阶段。** `startConnection` 接受一个观察者，在每个边沿上报——connecting、connected、reconnecting、failed——带上当前次数、次数上限、下次重试时间、本阶段起始时间、原因与最近一次已脱敏的错误。传输层的 `onerror` 也被捕获，于是进程崩溃能报出错误本身，而不是只有一个关闭事件。
- **一个注册表，一个端口。** `runtime/mcp/mcp-connection-registry.ts` 以派生的 serverName 为键保存最近一次观察；组合根通过 `CatalogPorts.mcpConnections` 读取，桥销毁时抹掉对应条目。用 serverName 作键，与状态构建器把工具归到套件的方式一致。
- **观察优先于工具快照，诊断优先于观察。** 连接掉线的行在监管器重试期间报 `degraded`、停止后报 `failed`，代码分别是 `reconnecting` 与 `reconnect-stopped`，最近错误成为该行的原因。从未挂载成功的行保留诊断原文，不携带连接字段。
- **面板说明并跟随它。** 卡片的正文行与详情状态带渲染「连接断开，正在重连（第 2/10 次）」并附最近错误。详情在一条活连接掉线时就提供重试，而不只在行已判定失败时，因为重试正是缩短等待的动作。正文行还会把等待倒计时写出来，「第 2/5 次」不再藏住这段停顿有多长。只要还有行在重连，面板就睡到监督者自己报的下一次尝试之后（下限 500ms、上限 15s，没有报时间的行退回短间隔），次数因此保持真实，而不用在长达一分钟的退避里轮询几十次；全部安定后停止。
- **重试策略本身不动。** 延迟保持 500ms 到 30s、共十次。30s 上限同时充当关闭一次中断的稳定窗口，调低会让崩溃循环的服务更早重置预算；缺的是可见性与手动路径，不是更短的阶梯。

## Alternatives considered

- **靠轮询宿主工具注册表推断中断。** 否决：重试期间工具一直在册，而这正是被读成健康的那个状态。
- **保留固定 1.5 秒轮询、只把等待写出来。** 否决：真正有价值的读取是尝试之后那一次，而监督者本来就报出了它的时间。
- **调低 `maxDelayMs` 让重连感觉更快。** 暂不采用：它同时缩短区分「已恢复」与「崩溃循环」的稳定窗口。现在这一行会说明等待时间，并提供结束等待的重试。
- **把现有日志行渲染出来当原因。** 否决：logger 不是界面，面板也没有回读通道。
- **一掉线就把行标成失败。** 否决：监管器还在重试，而 failed 无法区分「等待中」与「已放弃」。

## Consequences

- 连接注册表是进程级的；两个登记作用域监管同一个 serverName 时共享最近一次观察，这与状态行使用的身份一致。
- 有行在重连时，面板每 1.5 秒多一次状态读取，直到中断结束；停止或健康的行不增加读取。
- 状态行现在可能带 `connection` 记录，自己渲染 MCP 界面的消费方应优先读 `state` 与 `code`，而不是工具数量。

## Verification

- `packages/market-mcp/test/mcp-connection-observations.test.ts` 用真实监管器连接一个在握手前就退出的进程：阶段按顺序到达，每条重试边沿都写明下次次数与时间，预算在 gave-up 处停住，spawn 错误随行携带。
- `packages/market-bundle/test/integration/mcp-status.test.ts` 钉住行合并：重连观察把看似健康的行变成 degraded 并附最近错误；停止观察变成 failed；挂载诊断保留自己的措辞。
- `packages/market-bundle/test/integration/client-mcp-detail-actions.test.ts` 钉住重试可用性与连接句子的键形。
- 服务端、客户端与两个测试工程的类型检查均干净；触及的 MCP 测试（65 个）通过。
