# Agent Note：重新挂上的服务会忘掉重试预算

Status: implemented

## Problem

共享的 `RetryScheduler` 每个挂载键最多五次尝试，却在挂载后来成功时不重置计数。它的文档注释声称计数会随每次 reconcile 重置，但没有任何代码这么做。一个套件服务或语言服务器，如果在它的一生中跨几次互不相关的中断失败过五次，就再也无法重试：第六次失败只记一行「giving up」并且不再挂定时器。面板也没有任何动作能清掉这份预算，于是昨天还能用的服务可能一直保持着未挂载状态，直到宿主重启。这就是「重连很久、然后干脆不再帮忙」的成因之一。

## Decision

- **`RetryScheduler.settle(key)`** 取消该键的待定定时器并删除其次数。
- **两个注册表都在成功时 settle。** MCP 轮次对指纹仍然匹配的存活挂载、以及返回无失败的挂载调用 settle；LSP 轮次的两条存活路径同样调用。活着的挂载按定义不在崩溃循环里，而上限防的正是崩溃循环。
- **确定性跳过保持原规则。** 没有 reason 的目标依旧丢弃预算而不是挂定时器，这一点不变。

## Alternatives considered

- **调高 `MAX_RETRY_ATTEMPTS`。** 否决：只是把同一个缺陷推迟几次，之后预算照样永久耗尽。
- **每次 reconcile 清空所有预算。** 否决：崩溃循环的服务会被无限重试，而那正是上限要防的行为。
- **成功后重置整轮而不是按键。** 否决：一个健康的兄弟服务会给坏掉的服务无限续命。

## Consequences

- 挂上之后再失败的服务重新从 1.5s 开始，该次中断的节奏是 1.5s / 5s / 15s / 45s / 120s。
- 预算现在表示「连续失败次数」，这也一直是这个上限的本意。

## Verification

- `packages/market-runtime/test/retry-scheduler.test.ts` 钉住三种行为：五次失败耗尽预算、第六次静默；`settle` 让下一次失败从第一档延迟重新挂表；`settle` 取消待定定时器。
- 类型检查干净；MCP 与 LSP 的挂载测试通过。
