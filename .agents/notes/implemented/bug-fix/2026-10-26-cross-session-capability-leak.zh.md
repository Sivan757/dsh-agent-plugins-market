# Agent Note: 一次会话应用不得收窄另一会话的能力

Status: implemented

## Problem

在一个会话里切换扩展预设，有时会让另一个会话报告某个工具消失。两种机制产生同一症状：模型工具列表背后丢了一次挂载，以及调用被 `extension-resource-disabled` 拒绝。两者都是本插件共享状态记账的缺陷，不在宿主。

## Decision

两处所有者错了，现在各只有一个所有者。

### 目录权威属于目录流水线

一次会话应用把它刚读到的声明当作进程级权威发布（`runtime.setCatalogAuthority`）。此后每个其他会话的需求都通过那一次读取投影，于是一次残缺、过期或与来源更新赛跑的读取会卸载另一会话的 MCP 服务器并注销其工具。

`RuntimeReconciler.ensureCatalogAuthority` 仅在任何过程都尚未发布权威时播种。会话应用调用它，因此仍能投影自己的需求。`refreshCatalog` 仍是唯一能替换权威的写入者，而它唯一的调用方是目录流水线，每次变更都自带一次新读取。

### 失败即关闭的刷新不再永久

`ExtensionRuntime.refreshAgent` 对尚未就绪的会话、以及落在被取代世代里的成功刷新都会提前返回，留下 `stale` 与 `dirty` 且没有任何调度。`allows` 在 `stale` 时失败即关闭，于是每会话的闸门拒绝所有受管工具，而对空闲会话再没有东西回来。启动挂接窗口期间的任意目录变更就足够，而挂接窗口就是整个会话启动。

最差状态（stale 与 dirty 并存且无在飞工作）现在不可达：

- 每个提前返回与每次失败刷新都会安排下一次重试，延迟从基数开始翻倍，并稳定在上限，
- 只要会话仍被拒绝，调度就不会停止。用尽即放弃会把瞬时失败变成本次修复所针对的同一种永久拒绝，只是晚一分钟，
- 成功刷新会取消重试并清空其预算，
- 忙碌会话仍通过 `whenIdle` 自愈，若那一趟也没能完成，延迟那趟会安排重试，
- 从"未就绪"分支恢复会在 catch 中重读清单，然后刷新该智能体或安排重试，因为该分支只重放已提交选择而不读取任何东西。那里抛出也不会留下半恢复的智能体。

调度是 `inventoryRetry.baseMs` 与 `maxMs`，由 `resolveInventoryRetry` 一次性解析，默认 200 与 60000 毫秒。它们随部署变化，因此是经过校验的配置字段而不是常量，与开关预算遵循同一条规则。格式错误的值在加载时失败，基数高于上限会被拒绝而不是悄悄夹紧。

目录读取确实在挂起期间，失败即关闭的窗口不变：`allows` 仍然拒绝。消失的只是永久性。

### 拒绝现在有了名字

`ExtensionRuntime.denialReason(agent)` 在该智能体 stale 时返回 `extension-inventory-pending`，人真正会读到的两个面都带着它：

- 每会话工具闸门追加的原因里写明 `extension-inventory-pending`，并说明能力会自行恢复，而不是给出"请让用户启用一个已经启用的资源"那种撤销文案，
- 会话窗口发布 `status.inventoryPending`，预设菜单据此显示一行双语提示。读取失败时窗口改用缓存行作答，因此面板会说明原因而不是整个失败。

## Alternatives considered

- **只加重试，不观察就绪**被否决，因为重试是定时器，而稍后完成挂接的会话应当立刻被服务。延迟的 `whenIdle` 趟与重试共同覆盖两者，重试则负责关上空闲智能体的窗口。
- **只观察就绪，不加重试**被否决，因为就绪不是刷新卡住的唯一原因。清单读取可能在世代稳定时失败，而那没有任何东西会观察到。
- **重读一次后无条件清除 stale**被否决，因为它会授权一个确实已经消失的资源。反向对照是明确的：被撤销的套件仍然拒绝，重试永不复活它。
- **有界次数预算、用尽即放弃**被否决，因为放弃本身就是缺陷。预算用尽后被拒绝的会话正是本次修复要解决的被困会话，只是更晚、更安静。
- **把调度写成常量**依据仓库规则被否决：慢机器和大目录都会改变重读耗时，所以调度是策略，属于经过校验的配置。
- **只把失效范围缩到每个智能体读过的目录修订**被否决，因为它消除了跨会话触发，而没有消除永久性。一个无法完成自身刷新的会话仍会被困住。上面的权威改动就是收窄范围的修法，而这一项修的是永久性。
- **修宿主**依据证据被否决：`tools.restrict` 在无作用域时抛出、限制只过滤继承层、作用域挂载对另一智能体不可见、且没有缓存全局工具列表。机制完全在本地。

## Consequences

一个会话的预设应用不再能改变任何其他会话可挂载什么，目录变更也不再能把一个会话永久拒绝。代价是：

- 被拒绝的会话按逐渐变慢、以上限为稳态且永不停止的调度重试。清单持续不可读的会话保持工具被拒，在进入慢调度时记录一行日志，并在读取恢复后自行恢复。
- 状态面能区分挂起读取与被撤销资源，模型可见原因与预设菜单两处都有，因此失败不再只有模型能看到。
- 从"未就绪"分支恢复会多付一次清单读取。
- 清单读取失败不再让整个面板读取失败。

## Verification

`packages/market-bundle/test/integration/cross-session-mount-isolation.test.ts` 驱动真实协调器与真实 MCP 挂载注册表，对着回环 MCP 服务器。第二个会话带着残缺声明读取应用后，第一个会话的服务器仍保持挂载；目录流水线仍能收窄权威；首个播种者无法藏起另一会话之后会选中的套件；读取与已发布权威不一致的会话会以 `extension-shared-demand-unavailable` 被拒绝，而不是静默什么都不挂载。最后一条用例通过 `ExtensionRuntime` 跑两个真实会话：会话 A 用省略 B 套件的读取应用，B 的挂载与授权都保留。

`packages/market-bundle/test/integration/extension-stale-recovery.test.ts` 在真实 AgentLoop 上用真实工具注册表驱动真实 Agent：挂接窗口期间的目录变更不会让会话丢掉工具，清单读取失败在恢复后自愈，重试会越过旧的次数预算继续运行，确实被撤销的资源仍然拒绝并保持拒绝，模型可见原因里写明 `extension-inventory-pending`，会话窗口发布挂起标记并在恢复后清除，恢复自身刷新无法完成时仍会安排重试。

`packages/market-bundle/test/integration/inventory-retry.test.ts` 钉住调度：文档化的默认值、会稳定在上限且永不停止的翻倍、受基数与上限约束的延迟、拒绝热循环或永不运行的值、拒绝高于上限的基数、以及冻结的结果。

`packages/market-bundle/test/integration/client-extension-presets.test.ts` 为就绪会话渲染挂起提示，并断言它不是"未就绪"状态。

反向对照，各自撤销、命名测试失败、再恢复文件：

- 让 `ensureCatalogAuthority` 表现得像旧的 `setCatalogAuthority`：残缺读取用例失败，`expected ['demo/alpha'] to deeply equal ['demo/alpha', 'demo/beta']`。
- 让 `scheduleRetry` 空转：读取失败用例失败，授权保持拒绝。
- 去掉 `resolveInventoryRetry` 的校验：热循环用例失败，`expected [Function] to throw an error`。
- 去掉重试上限：调度用例失败，`expected [Array(8)] to deeply equal [100, 200, 400, 800, ...]`。
- 把闸门的挂起原因改成通用文案：模型可见用例失败，原因里不再含 `extension-inventory-pending`。
- 去掉窗口的挂起标记：窗口用例失败，`expected undefined to be true`。

挂接窗口用例在禁用重试时也通过，因为变为就绪本身会重读清单并清除标记。真正有区分力的是读取失败用例，而它正是稳定世代所产生的情形。
