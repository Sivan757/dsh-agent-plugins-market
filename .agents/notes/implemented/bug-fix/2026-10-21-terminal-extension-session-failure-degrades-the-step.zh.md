# Agent Note: 终止性 extension 会话失败降级该步

Status: implemented

## Problem

每个工作区会话在第一步之前都会跑一次 extension 会话启动。启动过程完成会话选择的 capture：先读工作区清单，再通过宿主应用这个选择。如果这次 capture 抛出，服务记录错误并把该 agent 标为不可用，pre-step 处理器随后拒绝进入一步：它把已认领的消息重新放回队列并 reject。宿主于是把这一轮以 `blocked` 结束，消息继续留在队列里。

对可恢复的失败来说，reject 是对的，因为后面有东西会重试它。会话启动失败没有这样的重试。`initialize` 是单飞的并会记忆错误，显式恢复会重跑同样失败的读取，而每个 agent 的状态按 Agent 对象存放。于是被那次 reject 挡住的请求永远等下去：每次发送都变成又一轮 blocked，agent 始终不启动。

issue #113 报告的是这个症状，起因是一个打包缺陷（[`files` 没有携带 schema](./2026-10-21-published-artifact-ships-its-schemas.zh.md)）。扫描在每次会话尝试中抛一次 `ENOENT`，于是每个工作区会话——新建或恢复——都在第一条用户消息之后停住。日志里第一次是启动，第二次是同一会话 id 的新 Agent 做同样失败的读取。

## Decision

`ExtensionSessionState` 记录失败的那次尝试是否就是会话启动本身。在下一次 pre-step 时，已记录的终止性错误会进入这一步而不是 reject，于是这一轮以降级方式运行。

终止性指三件事同时成立：错误来自 `initialize`，没有在途尝试，且错误码既不是 `extension-session-busy` 也不是 `extension-session-corrupt`。busy 挂载自己拥有空闲重试。corrupt 记录是不确定的日志，需要用户清除。其余没有重试兜底的失败都降级该步。

降级不授予任何东西。状态仍是未就绪并带错误，`read()` 仍抛 `extension-session-not-ready`，`ExtensionRuntime.allows` 拒绝，工具闸门拒绝，因此会话可以继续工作，而它管理的资源保持不可用。失败在两处可见：面板读 `status.error`，日志每个新错误码一条 `warn`。

在工作会话之后记录的失败保持旧契约：请求等待显式恢复重新应用已提交的选择，因为让一轮跑在半应用与已回滚的选择之间，比带恢复控件的等待更糟。启动失败标记会被任何已发布状态清除，因此这条区分是精确的。

## Alternatives considered

**在启动失败时装一个空的、fail-closed 的选择。** 这会让 `status` 报告就绪，选择也变成普通选择，于是这一轮无需特殊分支就能运行。代价是：对一个没有东西可恢复的失败，恢复控件消失了，而且发布了一个没人选择过的选择。每个读"没有选择即无授权"的消费方都得学会区分空真实选择与这个。

**停止重放并让这一轮无步结束。** 请求会被消费掉，既没有模型调用也没有回答，于是为从未运行的工作报告成功。进入这一步至少能回答用户，并说明管理资源不可用。

**给 blocked 轮数设上限再失败。** 计数改变的是会话何时放弃，不是请求何时被服务：没有重试兜底的 capture 每次尝试都以同样方式失败。

**按定时器重试 capture。** 仓库已经为挂载做了有界重试调度，但会话启动是一次性 capture，产生的是确定性错误。重试它只会在原因不变的情况下空耗轮次，而用户仍然不知道会话为什么是空的。

**改宿主，让 agent 不等插件就启动。** 宿主本来就支持：`enter` 决定本身不授予任何东西，进入与否是插件的决定。修法属于接缝的这一侧。

## Testing

`packages/market-bundle/test/integration/extension-session-scan-failure.test.ts` 用真实的 agent loop、记录型模型适配器和抛出打包产物 `ENOENT` 的清单端口来驱动：

- 新建时启动失败：一次清单调用，状态 `ready:false` 且 `error: 'ENOENT'`，随后一次用户发送到达模型且只有一次请求，这一轮以 `completed` 结束，工具闸门报告管理工具不可见；
- 恢复时启动失败：第一个 agent 提交一个选择后被释放，同一会话 id 的第二个 agent 用抛错的清单端口重放 apply。它同样到达模型，且只有一次清单调用；
- 会话恢复成功后再中途失败：请求重新被停放，这钉住了"发布后清除"规则存在的那条区分。

`extension-session-recovery.test.ts` 里两个用例编码了启动失败的旧"永久停放"契约，随契约一起更新：eligibility 不可判定那个与维护失败那个。两者仍然断言不授予任何资源。

## Related

这局部取代了 [串行化策略状态并恢复排队用户工作](../architecture/2026-10-08-policy-and-recovery-stability.md) 里的恢复规则：会话启动失败之后的请求不再等待显式恢复，而会话中途失败之后的请求仍然等待。它也给 [共享面与下一轮选择](../architecture/2026-10-08-shared-surfaces-and-next-turn-selection.md) 加了限定：那里的 busy 拒绝正是 `extension-session-busy` 路径，它保留自己的重试，因此永不走降级。两条决定都没有被完全取代。

## Consequences

extension 启动失败的会话，现在在用户恢复之前没有管理的 skills、commands、子代理、hooks、MCP 服务与 LSP provider。这是有意的权衡：能回答但没有管理资源的会话，好过永远起不来的会话。期待插件资源的用户会看到它们缺失，面板的错误会说明原因。

会话中途失败仍会停放请求。把降级规则放宽到所有失败，会让一轮跑在半应用与已回滚的选择之间，而恢复已提交的选择需要显式恢复控件。

启动失败标记在内存里并绑定 Agent，这是正确的：宿主重启会重放会话并做一次全新尝试，过期的标记会是错的。

issue #113 里的"每分钟数百次迭代"不是这个插件内部的空转。每次尝试恰好消耗一次扫描，所以倍增来自重新发起会话尝试的那一侧。这一侧的缺陷是一次尝试就足以让会话永久卡住，而这条决定消除了它。
