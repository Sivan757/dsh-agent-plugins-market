# Agent Note：宿主的支持下限跟随实测基线

Status: implemented

## Problem

每个宿主 pin 携带的支持窗口是 `>=0.2.0-rc.2 <0.3.0-0`。这个窗口写在 2026-10-17，当时 `0.2.0-rc.2` 正是宿主发布中的候选版本，此后没有再动过。

窗口声明两件事：这段代码能运行的最旧宿主版本，以及它永不跨越的大版本线。第一件事已经不再是可用的陈述——本仓库只在 `0.2.1-rc.5` 上构建和测试，流水线从未在 `0.2.0-rc.2` 上跑过。下限比 CI 验证的一切都旧，等于一句没有证据的承诺，还让消费者以为自己处在一个被支持的矩阵里。

宿主的候选线也已收敛：`@deepseek-ai/dsh` 的 `latest` 与 `next` 都指向 `0.2.1-rc.5`，之后没有更新的候选出现。

## Decision

- **下限改为实测基线：`>=0.2.1-rc.5 <0.3.0-0`。** 所有面向消费者的 pin（25 个 peer 与 6 个自供依赖）都从本仓库构建所用的版本起算，声明与证据一致。
- **上限保持 `<0.3.0-0`。** 宿主一个 minor 会搬动 seam——`ctx.get` 的形状、工具契约、本插件挂载的各个面。「感觉稳定」不是跨 minor 的兼容保证，复用台账与 seam 探针都是按 minor 校准的。
- **基线通道仍是 `next`。** 切回 `latest` 的书面触发条件是宿主发出第一个 stable。它还没发生： `0.2.1-rc.5` 仍是候选，而能力包的 `latest` 是首次发布的占位 `0.0.1-rc.1`——门禁若解析 `latest`，比对的会是一个没人安装的版本。

## 收窄窗口顺带删掉的东西

旧下限养着一处 workaround。仅用于开发的桥接包把 hook 协议声明为精确 peer，而 semver 会把旧窗口解析到下限 `0.2.0-rc.2`——与桥接声明的 `0.2.1-rc.5` 属于不同的 tuple——于是根目录的 `.pnpmfile.cjs` 把这一条 peer 边改写为 dependency 边，维持一份嵌套副本。旧记录写明了退场条件：下限升到桥接那一行时删除钩子。

新下限就是那一行。两侧现在都是 `0.2.1-rc.5`，`pnpm install` 只解析出一份副本，钩子、它自己的测试、以及锁文件里的 `pnpmfileChecksum` 都已删除。锁文件测试改为守终态：只有一份协议版本、位于声明下限上、且不存在能藏住第二份副本的钩子。

## Alternatives considered

- **把 `0.2.0-rc.2` 继续当作兼容性声明。** 否决：没有任何流水线验证它。一个从未被验证过的支持范围，在消费者于该版本上报告缺陷时无从辩护。
- **把上限放宽到 `<0.4.0-0`。** 否决：插件的宿主 seam 是按 minor 解析的（`ctx.get` 形状、工具契约），而 minor 正是它们变化的地方。
- **既然锚点包的 `latest` 与 `next` 一致，现在就切 `latest`。** 否决：这种一致只属于 `@deepseek-ai/dsh`；能力包仍是 `latest = 0.0.1-rc.1`，正是 2026-09-23 那次 `next` 决策要防的失败。
- **不动下限，只在文档里说明差距。** 否决：范围是机器可读的，消费者按它行动；脚注收窄不了它。

## Consequences

- 仍停在 `0.2.0-rc.x` 的消费者需要前进一个候选版本。它们是同一条 `0.2` 线的预发布，本插件的发布说明也写明了这次变化。
- 窗口内的任何宿主候选仍然不需要本仓库发版即可运行；只有插件主动放弃一条发布线时，下限才移动。
- 宿主发出 stable 版本时，必须在同一次改动里把门禁默认通道切回 `latest`，并把下限提到那个 stable。
