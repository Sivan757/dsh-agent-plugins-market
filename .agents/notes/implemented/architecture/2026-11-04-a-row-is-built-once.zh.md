# Agent Note：一行数据只构建一次，由展示它的面负责适配

Status: implemented

## Problem

同一行会出现两次：一次在它自己的设置页（属于工作区），一次在预设管理器里（属于某个预设）。两处画的是同一张卡片、回答的是同一组问题，而过去各自用自己的代码回答。失败句子写了两遍，开关动词写了两遍，工具数与传输方式的槽位也各填一遍。可预见的结果就是漂移：面板里新增的事实，只有有人记得才会出现在管理器里，而测试只能抓住它们已知的那几处副本。

## Decision

- **一个构建器，`client/ui/face-entry.ts`。** 每个面把自己的行类型适配成 `FaceRowFacts`，说明自己的模式，构建器返回共享卡片要渲染的 entry。状态条、状态词、开关是否存在及其动词、计数、底行与失败句子都在这里算。
- **两种模式只在两处不同。** 设置面说的是这一行在做什么（`已连接`、`失败`），预设说的是这一行在不在预设里（`已启用`、`已停用`）。并且预设区分两种「不能切换」——宿主统一管理的行，与背后根本没有东西的行——因为它持有宿主根本管不了的行。
- **失败句子只组合一次。** `liveFailureSentence` 是唯一跑 guidance 分类、保留建议、再附上尝试耗时的地方；两个面读同一个答案，所以一次慢失败在卡片与管理器里读起来一致。
- **先迁移管理器与两个服务面。** 它们同时存在两个面，事实也最丰富。撰写类面暂时保留自己的 entry 映射：它们的卡片带编辑与删除，而这个构建器刻意不拥有这些动作，而且它们已经共享筛选表与失败句子。

## Alternatives considered

- **共享面板组件，而不是共享 entry。** 否决：设置面板持有实时监管、重试处理器、弹窗与编辑器；这些都不属于管理器，搬过去是把小的重复换成大的耦合。
- **连状态词也统一。** 读了两边之后否决：`已连接` 回答「它在跑吗」，`已启用` 回答「它在我的预设里吗」。一个词兼两问，等于在提问的那一页上两个问题都没答。
- **在服务端生成 entry。** 否决：卡片是渲染决策，而服务端已经给出事实（`runtime`、`transport`、`toolCount`）；再造一条 entry 契约只是把逻辑重复变成契约重复。

## Consequences

- `FaceRowFacts` 上新添的事实同时到达两个面；漏掉一项会在构建器里成为类型错误，而不是某张卡片上静默缺失的一行。
- 预设管理器不再自带失败句子的组合逻辑，`runtimeWarning` 已删除。
- 其余面（市场、技能、快捷指令、专家、输出风格、系统提示词、钩子）仍在原地构建 entry。搬过去是机械工作，而且现在有了目标形状。

## Verification

- 实测，两面上的同一批行：`cloudflare` 在设置页读作 `套件 · https://mcp.cloudflare.com/mcp · 工具 4 · streamable-http`，在管理器里同样读作 `套件 · https://mcp.cloudflare.com/mcp · 工具 4 · streamable-http`；失败的 `kuboard` 两边都读作 `连接超时 · 10.0s`，来自同一次组合。只有状态词按设计不同。
- `face-entry.test.ts`（5 条）钉住这种对等：同一句失败描述、相同的事实、两处刻意的差异、没有开关的面不画开关、仅仅被停用的行不会被编出失败。
- 全量 2556 测试通过，门禁干净。
