# Agent Note: 项目 Agent 布局改为显式开启

Status: implemented

## Problem

项目原生布局（`.claude`、`.agents`、`.codex`、`.cursor`、`.kimi`、`.zcode`、`.qoder`、`.github`）此前默认扫描。只要会话的工作目录里存在这些目录之一，该项目的技能、命令、代理角色、MCP 服务与 hooks 就会静默进入会话：检出内容可以在无人选择的情况下改变会话提供什么，而从未打开插件卡的用户也无从知道工作目录贡献了内容。拒绝同样可行，但前提是先发现这个开关。

## Decision

`dsh-agent-plugins-market` 设置命名空间中的 `scanProjectLayouts` 默认值为 `false`：只有用户打开开关后，项目才贡献自己的布局。显式的 `true` 仍持久化在设置文档中并照常生效。

其余行为不变。开关仍在下一轮发现时生效，候选随之立即出现或消失；它仍会失效发现缓存与项目快照，也仍参与发现指纹，因此较早的扫描无法提供配置不同的快照。配置源、已安装套件与 `<project>/.dsh/agent-plugins` 项目状态在两种取值下都不受影响。

注册表、各客户端方言与项目运行时由[布局注册表决策](2026-09-09-layout-registry.zh.md)负责。本记录只负责默认值。

## Alternatives considered

**保留 `true` 并补充说明。** 拒绝：文档无法让注入在发生的那一刻可见。贡献内容的目录往往不是用户有意放进去的，而它加入的资源在面板中与已安装套件无从区分，除非用户已经知道要去看。

**存量安装沿用 `true`，新安装从 `false` 开始。** 拒绝：同一操作会因安装历史而行为不同，`settings.yaml` 里持久化的值也无法仅凭该文档解释。

## Consequences

此前贡献资源的项目在开关打开前不再贡献，因此依赖隐式行为的存量用户需要显式开启一次。作为交换，会话能力面的形成始终源于用户做过的选择，设置文档也完整陈述了答案。

该开关是持久化设置而非按项目的授权：打开后用户运行会话的每个项目都被纳入，也没有按仓库粒度的开启方式。如果将来需要这一粒度，项目内开启可以作为独立的改动。

## Verification

设置 schema 测试将缺失的 `scanProjectLayouts` 段固定为 `false`；项目发现测试固定同一项目在开关打开前不产出套件、打开后产出一个。[ADR](../../../../docs/developer/decisions/2026-09-09-layout-registry.md)记录了该开关与其持久化证据；其早先的设置界面验证是在默认值为 `true` 时进行的。
