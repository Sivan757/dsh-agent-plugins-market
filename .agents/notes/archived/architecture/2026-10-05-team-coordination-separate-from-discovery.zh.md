# Agent Note: Team 协调独立于角色发现

Status: implemented

## Problem

角色 Team 创建保留了 persona 与模型路由，但精简目录主要保留限制句及 API 说明，没有明确 Lead 负责需求沟通和方向，也没有说明如何在未知答案时分派调研。角色目录还可能为空，因此不能让它成为解释 Team 协作的唯一入口。

## Decision

`team-coordination.ts` 在宿主 Team 策略之后贡献一个动态 `market:team-coordination` 系统段。每次组装通过注册表和 Team 身份解析准确的活跃 Agent。Lead 文案涵盖授权后的主动分派、独立调研交底、范围与依赖归属、用户纠正、成员复用、避免重复劳动及验证后交付。成员文案涵盖身份、基于 target 的 Lead／同伴通信、范围内执行、决策升级及证据回报。无 scope、过期／伪造身份或非 Team 子代理不渲染该贡献。

该贡献只需 agents、agentTeams 和 systemPrompt，独立于角色发现、agents 资源过滤和增强创建的依赖。原生成员及无角色目录的会话仍获得同一协作约定。入口 inject 管理服务出现／消失，提示注册表负责释放；不新增逐 Agent 监听器／映射、计时器、轮询或名册。

角色目录负责名称与入口选择，工具描述负责 API 及生命周期语义。来源元数据中的指导文案指纹让旧目录在文案变化后的下一步更新一次，不依赖角色条目变化，也不改写历史。增强成员交底包含从 membership 取得的真实 Team 名，以及调用传入的可读目录名。内部角色身份仍留在未变更的持久快照 schema。创建消息和当前系统段刻意重复少量身份信息：前者是持久任务检查点，后者还覆盖原生成员、旧角色绑定及压缩后的新提示组装。协作流程只由系统段承载。

## Alternatives considered

- 扩展宿主策略或覆盖全局 AGENTS／记忆：否决，用户要求只改插件。现有授权及额外审批规则仍有效，新段不能自行授予权限。
- 把完整流程放回目录：否决，空／过滤后的目录和原生成员会缺失；再在工具描述和用户规则中重复会产生互相竞争的副本。
- 为每个 Agent 安装独立监听器和映射：不需要，已发布系统提示 section 的 text 回调可取得本次组装 scope。准确注册表身份与 Team membership 防止子成员收到保留的 Lead 指令。
- 重写第三方 skill、角色或 MCP 文本：否决，管理器就地转发作者内容；共享项目安全规范对 Lead 和成员仍有用。
- 把状态等待当成结果投递渠道：否决，宿主主动投递消息／结算通知；阶段性反馈不是最终完成声明，最终交付前仍须验证必要成员结果。

## Consequences

增强工具仍全局注册，并为每个非 Lead Agent 添加宿主作用域限制，同时拒绝继承可见性。插件卸载会移除注册和限制，执行时仍检查 Lead 身份。角色匹配以目录和增强工具均可用为条件，原生创建仍是回落，包括 fork。不会鼓励 Lead 仅为取得模型参数而选择不合适的角色。阻塞问题连同建议决策交给 Lead，不受阻部分可继续；重叠任务要求明确交接。这些是模型指令，不是锁或新增权限。

系统指令增加少量持续贡献，而不是重复发送流程目录消息；文案沿用现有模型契约的固定英文。角色卡编辑、路由优先级、持久 schema 和原生 Team 管理不变。运行时模块修改需消费它的宿主重新加载，仅构建不会更新已有进程。

## Testing

真实已发布 AgentLoop、Team 和提示服务覆盖已有／新 Lead、无角色目录的原生成员、两个独立 Team、空／伪造／非 Team scope、重复 compact 通知、原生策略之后的排序与卸载。角色成员测试检查首轮及冷恢复的 persona 和仅成员协调说明，同时保留创建消息与持久身份。测试断言实际组装／请求中的系统文本，不只检查注册字符串；不宣称已通过 A/B 证明自主模型行为改善。
